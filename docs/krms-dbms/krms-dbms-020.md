![](img/5340d9e794becb8555684d8343217b65_1.png)

在本节课程中，我们将深入学习如何为一个数据库实体选择一个合适的主键。主键是关系数据库设计的核心，它不仅能确保数据的实体完整性，还与外键共同维护着关系完整性。一个设计良好的主键对于数据库的性能、可扩展性以及数据安全性都至关重要。

## 主键的核心作用

上一节我们介绍了实体完整性的概念，本节中我们来看看主键如何具体实现这一目标。主键的主要功能是**唯一标识**实体中的每一个实例。这确保了在数据库表中，没有两行记录是完全相同的。我们可以用以下公式来描述主键的唯一性约束：

```
对于表 T 中的任意两行记录 R1 和 R2，其主键值 PK(R1) ≠ PK(R2)
```

## 理想主键的特征

那么，如何判断一个属性是否适合作为主键呢？以下是选择主键时需要考虑的一系列理想特征：

*   **唯一性**：这是最基本的要求，每个实例的主键值必须不同。
*   **非智能性**：主键值本身不应包含业务含义或需要经过计算得出。它应该是一个简单的标识符。
*   **稳定性**：主键值一旦分配，就不应再改变。例如，使用“姓名”作为主键就非常糟糕，因为姓名可能会变更。
*   **单一属性**：理想情况下，主键应由单个属性构成，这被称为简单主键。这比使用多个属性的复合主键更高效。
*   **数值型**：与字符串相比，数值型数据（如整数）在进行查询、索引和连接操作时速度更快。
*   **安全性**：主键不应包含敏感信息（如社会安全号码），因为这些值可能会在系统日志、URL或日常交流中被频繁使用。

## 自然键与代理键

有时，数据中本身就存在一个符合上述大部分特征的“自然键”，例如员工的工号或学生的学号。克莱姆森大学的CUID（用户ID）就是一个很好的例子：它是数字、唯一、稳定且非智能的。

然而，自然键有时会存在问题。以社会安全号码为例，它虽然是唯一的自然标识符，但因为它属于敏感信息，将其作为主键会带来安全风险，因此不是一个好选择。

当没有合适的自然键，或者自然键存在安全、长度或复杂性等问题时，我们可以使用“代理键”。代理键是由数据库系统自动生成的、没有任何业务含义的标识符，通常是一个自增的整数。

以下是使用代理键的主要优势：
*   **保证唯一性**：DBMS（数据库管理系统）自动管理，确保永不重复。
*   **性能优异**：通常是紧凑的整数，索引效率高。
*   **稳定性与安全性**：没有业务含义，不会改变，也不涉及敏感信息。
*   **简化设计**：特别是在处理多对多关系的桥接表或弱实体时，可以避免使用冗长的复合主键。

## 复合主键的使用场景

虽然我们推荐使用单一属性的主键，但在某些特定设计场景下，复合主键（由多个属性组成）也是合理且有用的。

主要有以下两种情况：
1.  **桥接实体（解决多对多关系）**：当创建桥接实体来连接两个多对多关系的表时，将两个源实体的主键组合起来作为桥接表的复合主键，可以清晰地表达这种关系。例如，在“学生-选课-课程”模型中，“选课”表的主键可以是 `(学生ID， 课程代码)`。
2.  **弱实体**：为了显式地表示弱实体对其父实体的强依赖关系，可以将父实体的主键作为弱实体主键的一部分。例如，“订单明细”表的主键可以是 `(订单ID， 产品ID)`。

## 案例分析：为何需要代理键

考虑一个“活动安排”实体，它包含以下属性：日期、开始时间、结束时间、房间号、活动名称、参与人数。

观察这些数据，你会发现很难找到一个天然的唯一标识符。日期、时间、房间都可能重复；活动名称也可能相同（如系列讲座）；参与人数更不可能唯一。如果强制不使用代理键，你可能需要将所有6个属性组合成一个庞大的复合主键，这非常低效。

在这种情况下，最优雅的解决方案就是引入一个代理键，例如 `活动ID`。数据库可以自动为每个新活动生成一个唯一的ID（1， 2， 3...），完美解决了标识问题。

```sql
-- 创建带有代理主键的‘活动’表示例
CREATE TABLE Events (
    event_id INT PRIMARY KEY AUTO_INCREMENT, -- 代理键，自增
    event_date DATE NOT NULL,
    start_time TIME NOT NULL,
    -- ... 其他属性
);
```

## 总结

本节课中我们一起学习了选择合适主键的艺术。我们明确了理想主键应具备**唯一、非智能、稳定、简单、数值化且安全**的特征。我们比较了**自然键**和**代理键**的适用场景，认识到在缺乏合适自然键或出于安全、性能考虑时，由系统生成的代理键是更优的选择。同时，我们也了解了在**桥接实体**和**弱实体**中使用复合主键的特定设计模式。理解这些原则将帮助你设计出更健壮、高效和安全的数据库结构。
