# Android中实时拦截剪切板请求的实现思路



**起因**



我本身非常讨厌应用一打开就读取我的剪切板。感觉很火大我开发了一款全局作用域的 xposed 模块仅放行 Gboard 的剪切板读取请求。



但是问题是 Android 的应用内长按粘贴请求也被拦截了只能在 gboard 内手动粘贴。



我发现在 ios 中应用主动请求剪切板内容和应用请求剪切板是分离的。在 ios 下应用想要读取剪切板会弹出一个弹窗让用户选择是否允许，在我看到后就知道这就是我想要的然后就开始了我模块的改进工程。

**遇到的问题**



在我询问 LLM 剪切板的调用链条时我发现这是一个非常复杂的任务。Android 的剪切板读取是通过 aidl 向 system_service 进程直接请求的同步方法。这就让我非常困扰。



首先 hook 点位应该在哪？我是应该在应用进程里把同步的函数进行移异步实现还是在 system_service 内的 ClipboardService 进行修改呢？

- 方案 1 如果修改应用进程内的函数实现应该是最简单的，但是我不想这样。首先每个人应用都会被 xposed 注入而且在 lsposed 框架下只有被勾选的应用才能生效，和我之前的全局生效的比还开了倒车

- 方案 2 如果 hook 点位在 ClipboardService 如何把这个同步函数内做到这个功能？弹窗又该怎么弹出？

**思考与尝试过程**



对于权限申请弹窗我第一个想到的就是Android的原生支持的权限弹窗。比如获取定位“看上去”就是一个实时允许和拒绝的api。而实际上这并不是实时生效的，也就是说Android的权限系统设计允许和拒绝在一个进程就是一次性的，这就让我傻了眼。



为了克服方案1直接注入导致的lsposed必须每个应用都注入一遍的问题我曾经尝试过直接修改系统的标准运行库。只要我把这个的代码改了自然所有进程的逻辑也会被同时修改，但通用性实在太差经过了基础的可行性验证方案1已经被我彻底放弃。



那么只有一条路在系统层的某个必经函数进行hook，并通过某种方式实现弹窗和获取用户选择。并且有必要的对app本身赋予某些特权确保整套流程不会被Android性能优化或权限系统影响

**解决方案**



既然为了全局生效且不注入应用程序层这一需求。那么应该选择的 hook 点位就是 system_service 进程的 com.android.server.clipboard.ClipboardService。所有的剪切板请求最后都会在这里处理。

```
val clipboardService = HookBridge.findClass ("com.android.server.clipboard.ClipboardService", lpparam.classLoader)
val clipboardImpl = HookBridge.findClassIfExists (
      "com.android.server.clipboard.ClipboardService\$ClipboardImpl",
      lpparam.classLoader
)
// 进行剪切板读取事件的拦截
hookClipboard (clipboardImpl ?: clipboardService)
hookAnrExemption (lpparam.classLoader)
```

既然 hook 函数确定了怎么把弹窗弹出来呢？



经过尝试得知 system_service 进程无法弹出，那么弹窗只能由 app 进行实现。



经过尝试最终敲定了 hook 和 app 通信方案。我在 App 中实现了一个 Service，让 system_service 进程在开机时自动连接 app 通过 aidl 进行通信。如发现断开则立刻重连。这样的设计不止可以用于普通通信还可以实现配置文件的实时更新，由于 App 内的 Service 没什么技术含量在这里只放 hook 端的代码。

```
object Client {

    @Volatile
    private var sService: IService? = null

    // 绑定客户的 Service 绑定核心代码
    private fun ensureBound (ctx: Context) {
        // 解冻 App，确保 Binder 能够正常拉起服务
        unstopPackage ()

        val intent = Intent ().apply {
            component = ComponentName (TARGET_PKG, ArirangService::class.java.name)
            addFlags (Intent.FLAG_INCLUDE_STOPPED_PACKAGES)
        }

        // 以 SYSTEM 用户身份绑定 Service
        withCleanCallingIdentity {
            ctx.bindServiceAsUser (
                intent,
                conn,
                Context.BIND_AUTO_CREATE or Context.BIND_IMPORTANT,
                UserHandle.SYSTEM
            )
        }
    }

    // 剪贴板权限异步拦截请求与 App 内 service 交互
    fun requestClipboardReadAccess (pkgName: String, uid: Int, userId: Int): Boolean {
        val service = sService ?: return FAIL_OPEN_WHEN_SERVICE_UNAVAILABLE

        val latch = CountDownLatch (1)
        val decision = AtomicInteger (Int.MIN_VALUE)

        // 通过 Binder 异步回调获取判定结果
        service.requestClipboardReadAsync (pkgName, uid, userId, object : IClipboardDecisionCallback.Stub () {
            override fun onDecision (result: Int) {
                decision.set (result)
                latch.countDown ()
            }
        })

        // 等待弹窗授权
        return if (latch.await (CLIPBOARD_CALL_TIMEOUT_MS, TimeUnit.MILLISECONDS)) {
            decision.get () == RESULT_ALLOW
        } else {
            FAIL_OPEN_ON_TIMEOUT
        }
    }

    // 配置读取与本地缓存
    fun readConfigSnapshot (configName: String): String? {
        val cache = configCache.getOrPut (configName) { CachedConfig () }

        if (cache.snapshot == null || isExpired (cache)) {
            configRefreshExecutor.execute {
                sService?.readConfigAsync (configName, object : IConfigSnapshotCallback.Stub () {
                    override fun onConfig (version: Long, snapshot: String?) {
                        cache.snapshot = snapshot
                        cache.version = version
                    }
                })
            }
        }
        return cache.snapshot
    }

    // 解除应用的 Stopped 状态，主要防止因为省电策略后台管理等状态无法连接
    private fun unstopPackage () {
        val b = ServiceManager.getService ("package")
        val ipm = IPackageManager.Stub.asInterface (b)
        ipm.setPackageStoppedState (TARGET_PKG, false, 0)
    }
}
```

在 ClipboardService 读取请求触发后向 app 发送一个剪切板读取请求然后阻塞等待返回结构，应用在受到请求后弹出弹窗请求是否返回。根据用户返回结果判断是否放行。由于这是在 system_service 进行的阻塞有系统彻底卡死的风险需要在 hook 的阻塞端加上超时机制一旦超时则不再等待返回结果直接拒绝。

```
private fun hookClipboard (targetClass: Class<*>) {
    val hookCallback = beforeHookedMethod {
        val callingPackage = args.firstOrNull { it is String } as? String ?: return@beforeHookedMethod
        val uid = Binder.getCallingUid ()
        val userId = (args.firstOrNull { it is Int } as? Int)
            ?.takeIf { it >= 0 }
            ?: runCatching {
                HookBridge.callStaticMethod (UserHandle::class.java, "getUserId", uid) as Int
            }.getOrDefault (uid / PER_USER_RANGE)

        // 对请求 uid 进行检查
        if (uid == Process.INVALID_UID || shouldBypass (callingPackage, uid)) return@beforeHookedMethod

        beginPending (uid)
        try {
            // 向客户端发送请求获取客户端 app 的回复
            val allowed = Client.requestClipboardReadAccess (callingPackage, uid, userId)
            if (!allowed) {
                HookLog.i (HookLog.Module.CLIPBOARD, "denied read for $callingPackage uid=$uid")
                result = null
            }
        } finally {
            endPending (uid)
        }
    }

    HookBridge.hookAllMethods (targetClass, "getPrimaryClip", hookCallback)
}
```

还有需要解决的问题就是一旦阻塞超过 5 秒 ANR 会弹出未响应弹窗。初版方案把超时时间设定在了 5 秒不过时间有点太短了。在后续的改进版本中为了解决该问题添加了通过伪造Debugging状态为当前阻塞应用授予临时特权的代码实现并将超时时间延长到了 10 秒

```
private fun hookAnrExemption (classLoader: ClassLoader) {
    val hookCallback = beforeHookedMethod {
        val uid = runCatching {
            if (thisObject.javaClass.simpleName == "ProcessRecord") {
                HookBridge.getIntField (thisObject, "uid")
            } else {
                HookBridge.getIntField (thisObject, "mUid")
            }
        }.getOrNull ()

        if (uid != null && pendingUids [uid]?.get ()?.let { it > 0 } == true) {
            HookLog.i (HookLog.Module.CLIPBOARD, "Bypassing ANR for uid $uid via isDebugging spoof")
            result = true
        }
    }

    runCatching {
        val processRecordClass = HookBridge.findClass ("com.android.server.am.ProcessRecord", classLoader)
        HookBridge.hookAllMethods (processRecordClass, "isDebugging", hookCallback)
    }
    runCatching {
        val wpcClass = HookBridge.findClass ("com.android.server.wm.WindowProcessController", classLoader)
        HookBridge.hookAllMethods (wpcClass, "isDebugging", hookCallback)
    }
}
```

**总结**



由于 Android 的 api 设计的历史遗留问题过于严重。想要完美复现 ios 内的剪切板体验还是没有做到只有一个我个人尽力而为的妥协实现。应用内长按粘贴也会呼出弹窗不过这也是没办法的事情。



由于我的模块的实现范围已经从简单的权限拒绝拓展为了从 Android 的框架中另立朝廷只进行剪切板修改就有点太浪费了，我就把这个模块从简单的剪切板拦截模块拓展了一系列其他的功能不过这都是后话了
