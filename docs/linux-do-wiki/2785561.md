# Java开发教程19-线程安全



本期是Java开发教程系列的第十九期,本期讲**线程安全**:多线程同时抢同一个数据会出什么事,以及怎么用 `synchronized`、原子类、线程池来对付.这是多线程最容易踩坑、也是面试最爱问的话题.若你已经熟悉竞态条件、`synchronized` 和线程池基本用法,可以跳过本期内容.

**一、竞态条件:三个线程抢一个数**

先看一个"看起来没毛病"的程序:100 个线程各自把计数器加 1,最后应该是 100:

```
public class Race {
    static int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[100];
        for (int i = 0; i < 100; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 10000; j++) {
                    count++;
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) {
            t.join();
        }
        System.out.println("count = " + count);   // 期望 1000000,实际经常不是
    }
}
```

多跑几次,`count` 经常不是 1000000,而是小一些的随机数.为什么?

因为 `count++` **不是一步,是三步**:读出 count → 加 1 → 写回.两个线程可能同时读到同一个数(比如都是 5),各自加 1 后都写回 6 !**两次加 1,只加了 1**.这种"多个线程同时读写共享数据,结果取决于执行顺序"的问题,叫**竞态条件**(也叫竞争).

这里给三条结论:

1. 多线程共享的**可变数据**,读写必须受保护

2. 变量"变化"得越小,越难出问题——能只读共享,就不改共享

3. 这次结果错没错是运气问题,不是逻辑问题,所以特别难查

**二、synchronized:把"三步"锁成"一步"**

要让 `count++` 的三步在某个线程执行时**不被别人插队**,用 `synchronized`(同步锁).它像公共厕所的门锁:一个人进去锁门,别人只能等,出来才轮到下一个.

**锁住一段代码**(同步代码块):

```
static Object lock = new Object();     // 一把锁(随便一个对象都行)

public static void add() {
    synchronized (lock) {              // 进门前要拿锁,拿不到就在门口等
        count++;
    }
}
```

**锁住整个方法**(同步方法,效果同上):

```
public synchronized void add() {   // 实例方法:锁是 this
    count++;
}

public static synchronized void add() {   // 静态方法:锁是当前类的 Class 对象
    count++;
}
```

规则只有一条:**同一个锁,同一时刻只能被一个线程持有**.我们代码里所有 `synchronized (lock)` 用的是同一个 `lock` 对象,所以 `count++` 的完整三步一定连着做完,不会被插队.换成两个不同的锁对象,锁就白上了:**锁的是同一把锁才有互斥**,这是新手最常犯的错.注意区分两类同步方法:`synchronized` 加在**实例方法**上,锁是 `this`(各实例一把锁,两个不同对象之间不互斥);加在**静态方法**上,锁是当前类的 `Class` 对象(全局唯一,所有调用都互斥).

把第一节的 `count++` 换成 `synchronized` 版本,结果就稳定是 1000000.代价是**性能**:每次加锁都有开销,且其他线程要等.所以锁的粒度要小:能锁一行,别锁一个循环;能锁共享数据的那几行,别锁整个方法.

> 顺带说一句:`synchronized` 保证的不仅是"不插队"(原子性),还有"改完别人能看到"(可见性).同一把锁保护下的读写,都能看到彼此的最新结果.

**三、volatile:只解决"看不见",不解决"抢着改"**

还有一个诡异问题:某个线程改了变量,另一个线程**读到的还是旧值**——不是抢着改,是"看不见".

```
static boolean running = true;

// 线程 A:等 running 变 false
new Thread(() -> {
    while (running) { }        // 可能永远空转,看不见 B 的修改
}).start();

// 线程 B:改 running
Thread.sleep(100);
running = false;               // A 可能永远不知道
```

原因是 JVM 会优化,把 `running` 缓存到每个线程自己的"副本"里,不保证立刻同步给别人.给变量加 `volatile`,强制**每次读写都直接操作主内存**,别人改的立刻可见:

```
static volatile boolean running = true;
```

但注意 `volatile` 只能保证"看得见",**不能保证"不插队"**:`count++` 那三步照样可能被插队,两个线程都读到 5 各自加成 6、最后写回还是丢一次更新,加 `volatile` 也救不了.一句话记住:**volatile 管可见性,synchronized 管互斥(也顺带管可见性)**.像"开关标志"这种只有一个线程写、别的线程只读的变量,`volatile` 足够;要"改数据",用 `synchronized`.

**四、原子类:不用锁的计数器**

能不能让 `count++` 天生就是"一步"?用 **原子类**.`AtomicInteger` 的 `incrementAndGet()` 把"读-改-写"做成一个**不可分割**的操作:

```
import java.util.concurrent.atomic.AtomicInteger;

static AtomicInteger count = new AtomicInteger(0);

// 线程里:
count.incrementAndGet();   // 相当于 count++,但整个操作原子化
```

## 底层用的是 **CAS**(Compare And Swap,比较再交换):“看看现在是不是我记着的值,是,就换新值,不是,说明别人改过了,重新读再试”.因为不锁、不阻塞,高并发下比 `synchronized` 快.这里只记结论:**原子类 = 针对单个变量的线程安全计数器,底层 CAS**.

**五、线程池初识:别裸奔着开线程**

每执行一个任务就 `new Thread(...).start()`,小项目没问题;任务一多(比如同时 1 万个请求),问题就来了:**创建线程本身有开销**(申请资源、建栈),而且线程数无限膨胀会把机器拖垮.解决:**线程池**.提前建好几个线程放着,任务来了交给它们干,干完不销毁,继续接下一个.

```
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

// 建一个固定 4 个线程的池子
ExecutorService pool = Executors.newFixedThreadPool(4);

// 丢 10 个任务进去,4 个线程轮流干
for (int i = 1; i <= 10; i++) {
    int taskId = i;
    pool.execute(() -> System.out.println("任务 " + taskId + " 由 "
            + Thread.currentThread().getName() + " 执行"));
}

pool.shutdown();   // 收工:不再接新任务,干完手头的就退出
```

你会看到只有 4 个线程名轮流出场,10 个任务排队干完.线程被**复用**了.

线程池的底层是 `ThreadPoolExecutor`,它的构造器有 7 个参数,先认识最核心的 3 个(剩下 4 个第 133 期"线程池深入"展开):

```
new ThreadPoolExecutor(
    4,          // 核心线程数:平时常驻的线程数,没活干也不销毁
    8,          // 最大线程数:任务排队满了还能临时再加几条
    ...         // 还有:空闲存活时间、工作队列(排队的位置)、拒绝策略等
)
```

一句话理解:**核心线程常驻 → 任务多了先进队列排队 → 队列也满了再扩到最大线程数 → 还塞不下就按拒绝策略处理**.第 12 期的成绩管理系统不用线程池;但你以后写服务器、写下载器,第一条原则就是"**用线程池,别裸 new Thread**".

**六、小项目:抢票加锁**

经典场景:100 张票,10 个线程抢,不加锁会"超卖"(卖出超过 100 张).

文件 `Ticket.java`:

```
public class Ticket {
    private int total;                 // 剩余票数
/**
 * 实际上我们总共100个位置不应该允许在线卖出100张票
 * 因为还要考虑到不会在线操作的消费者群体,实际售出应该适当减少比例
 * 面试考的是能力更是情商
*/
    public Ticket(int total) {
        this.total = total;
    }

    // 售票:没票返回 false,有票卖一张
    public synchronized boolean sell() {
        if (total <= 0) {
            return false;
        }
        total--;                       // 读-改-写三步,靠 synchronized 锁成一步
        return true;
    }
}
```

文件 `Main.java`:

```
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Ticket ticket = new Ticket(100);
        int[] sold = {0};              // 计数器(数组是为了让 lambda 能改它)

        Thread[] buyers = new Thread[10];
        for (int i = 0; i < 10; i++) {
            buyers[i] = new Thread(() -> {
                while (ticket.sell()) {
                    sold[0]++;
                }
            });
            buyers[i].start();
        }
        for (Thread t : buyers) {
            t.join();
        }

        System.out.println("卖出的票数: " + sold[0] + " / 100");
        // 没有 synchronized 时会看到 > 100(超卖)
    }
}
```

动手实验(这个实验非常值得做):

1. 把 `sell()` 的 `synchronized` 删掉,多跑几次,大概率出现卖出数 > 100——**超卖复现**

2. 加回 `synchronized`,稳定输出 100

3. 把 `int total` 换成 `AtomicInteger total`,`sell` 里用 `decrementAndGet()`,去锁版也能稳定 100,体会"原子类替代锁"

**朝花夕拾:第 18 期的下载器,任务多了怎么办**

上一期的多任务下载,我们手工 `new` 了 3 个线程,还好只有 3 个.如果下载列表有 1000 个文件呢?手工起 1000 个线程?那会把机器拖垮.今天学的线程池正是答案:任务丢进 `ExecutorService`,固定 4 条线程轮流下载,既复用了线程,又不会无限膨胀.

预告:第 10 期学的 `ArrayList`,在多线程下同样是"读-改-写"问题的重灾区:`add` 也会丢数据.线程安全的集合(`CopyOnWriteArrayList`、`ConcurrentHashMap`)在后期讲,今天先把"为什么"打牢.

**总结**

本期KO了多线程的"捣蛋鬼":

- **竞态条件**:`count++` 是读-改-写三步,多线程插队就丢更新,结果随机

- **synchronized**:同一把锁互斥,把关键步骤锁成整体;锁粒度越小越好

- **volatile**:解决"看不见",不解决"抢着改";开关类标志用它

- **原子类**:`AtomicInteger` 把单变量操作做成不可分割,底层 CAS,无锁更轻快

- **线程池**:核心线程 → 队列排队 → 扩到最大线程 → 拒绝策略;别裸 `new Thread`

- 抢票加锁小项目:删锁复现超卖,加锁/原子类修复
