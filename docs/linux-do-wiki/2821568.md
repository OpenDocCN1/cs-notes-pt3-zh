# Java开发教程25-JUnit



本期是Java开发教程系列的第二十五期,本期介绍**单元测试 JUnit**:给代码写"自动化检查",从此改代码不怕改坏.前 24 期我们验证程序全靠运行 main 手动看输出,今天开始交给机器.若你已经熟悉 JUnit 5 的 `@Test`、断言和生命周期注解,可以跳过本期内容.

**每期叠甲**:



时间仓促,水平有限,文中难免存在缺点和错误,恳请广大开发者和从业者指正.

---

**一、为什么需要测试:改代码最大的恐惧**

想想第 12 期的学生成绩管理系统:你修了一个 bug(比如删除的逻辑),怎么知道没把别的功能改坏?之前的办法是:重新跑一遍程序,把增删改查每个功能**手动点一遍**,看输出对不对.功能一多,这个"手动回归"越来越耗时,还容易漏 ![:distorted_face:](img/704374cc3bdbbb947740876b464e0c74.png)今天忘了查排序,明天就带着 bug 上线.

**单元测试(unit test)就是把"检查"写进代码**:对每个方法写一小段"验证程序",跑一遍,它自己告诉你过没过.从此:

1. **改完代码跑一次测试**,全绿 = 没改坏

2. **测试是活的文档**.它比注释更可靠地告诉你"这个方法应该怎么用、结果应该是什么"

3. **测试先红了才知道写错了**,不用靠肉眼盯输出

Java 最主流的测试框架是 **JUnit**,本期用 JUnit 5.

---

**二、环境:引入 JUnit 5**

在项目的构建文件里加依赖(Gradle):

```
dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter:5.11.0'
}

test {
    useJUnitPlatform()
}
```

IDEA 里同步后,测试代码放在**专门的 test 目录**(和 main 目录平级),IDEA 新建项目模板自带.写测试的类名一般用 `XxxTest`,比如给 `StudentManager` 写的测试叫 `StudentManagerTest`.

---

**三、第一个测试:@Test + 断言**

测试方法用 `@Test` 标记,方法体里写**断言**(assert):“我断言这个结果是 2,如果不是,测试失败”:

```
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

public class CalculatorTest {

    @Test
    void add_两个正数相加() {
        Calculator calc = new Calculator();
        assertEquals(5, calc.add(2, 3), "2+3 应该等于 5");
    }
}
```

跑法:IDEA 里类名左边有绿色三角,点它运行;或者 `gradle test`.绿了表示通过,红了表示断言失败.

**常用断言一览**:

| 断言 | 含义 |

| --- | --- |

| `assertEquals(期望, 实际)` | 相等(用 equals 比较) |

| `assertTrue(条件)` / `assertFalse(条件)` | 条件为真/假 |

| `assertNotNull(对象)` / `assertNull(对象)` | 不为空/为空 |

| `assertThrows(异常类, 可执行体)` | 断言"会抛这个异常" |

`assertThrows` 专门测异常场景,比如第 9 期的 `Integer.parseInt("abc")`:

```
@Test
void 非法数字_抛异常() {
    assertThrows(NumberFormatException.class,
            () -> Integer.parseInt("abc"));
}
```

lambda 里放"预期会炸的代码",不炸就测试失败 ![:bili_114:](img/19d9c19e66a084274937aaa50f2923b3.png)异常处理(第 8 期)的代码从此也有测试覆盖了.

**四、生命周期:@BeforeEach / @AfterEach**

多个测试方法通常需要"同一个准备动作":给 `StudentManager` 塞几个学生、连数据库、清临时文件.每个测试都写一遍太啰嗦,用生命周期注解:

```
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

public class StudentManagerTest {
    private StudentManager manager;

    // 每个测试方法运行前,都会先执行一次这个方法
    @BeforeEach
    void setUp() {
        manager = new StudentManager();
        manager.add(new Student("小明", 92));
        manager.add(new Student("小红", 58));
    }

    // 这里用中文是可以的,编译时无论汉语英语都会被编译为字节码
    @Test
    void 添加学生_数量增加() {
        manager.add(new Student("小刚", 76));
        assertEquals(3, manager.all().size());
    }

    @Test
    void 删除学生_数量减少() {
        manager.remove("小明");
        assertEquals(1, manager.all().size());
    }
}
```

`@BeforeEach` 的神奇之处在于**每个测试都是全新的 manager**:因为每个测试方法执行前都会重建.这样测试之间互不污染,顺序打乱跑也一样.

对应关系:

| 注解 | 时机 |

| --- | --- |

| `@BeforeEach` | 每个测试方法之前执行 |

| `@AfterEach` | 每个测试方法之后执行(清资源) |

| `@BeforeAll` | 整个测试类跑之前,只执行一次(要 static) |

| `@AfterAll` | 整个测试类跑完之后,只执行一次 |

还可以用 `@DisplayName` 给测试起中文名,失败报告里更好看:

```
@Test
@DisplayName("删除不存在的学生返回 false")
void removeMissing() {
    assertFalse(manager.remove("不存在的名字"));
}
```

**测试方法命名**:推荐"行为描述式",一眼看懂测什么:`删除不存在的学生_返回false`.方法名就是需求文档.

**五、一个测试只验证一个行为**

新手常犯的错:一个测试方法里塞一堆断言,一条不过就全红,还要猜是哪个挂了.好习惯:

- **一个测试方法 = 一个行为的一个方面**

- 断言失败会**立刻停止**当前测试并报告,所以拆开才能知道哪儿挂的

- 测边界(空列表、null、0、最大最小值)和异常,比测正常路径更容易暴露 bug

范例对比:

```
@Test
void 平均分_有数据时算对() {
    manager.add(new Student("小刚", 76));
    // 92 + 58 + 76 = 226,平均 75.333...
    assertEquals(75.333, manager.average(), 0.001);   // 浮点要带误差,见下
}

@Test
void 平均分_空列表返回0() {
    StudentManager empty = new StudentManager();
    assertEquals(0.0, empty.average(), 0.001);   // 浮点结果,要带误差项,见下
}
```

注意浮点断言:**assertEquals 比较 double 要带第三个参数(允许误差)**:因为 75.333… 在二进制里存不精确,直接相等会失败.`assertEquals(75.333, actual, 0.001)` 表示"差在 0.001 以内算过".

**六、小项目:给 StudentManager 写测试**

把第 12 期的 `StudentManager`(学生成绩管理系统)搬到项目里,给它写一套完整测试.类结构回顾:`add` 添加、`remove(name)` 删除、`updateScore(name, score)` 改成绩、`average()` 平均分、`max()`/`min()` 最高最低、`all()` 原始列表.

文件 `StudentManagerTest.java`:

```
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

public class StudentManagerTest {

    private StudentManager manager;

    @BeforeEach
    void setUp() {
        manager = new StudentManager();
        manager.add(new Student("小明", 92));
        manager.add(new Student("小红", 58));
        manager.add(new Student("小刚", 76));
    }

    @Test
    @DisplayName("添加:数量增加")
    void add_数量增加() {
        manager.add(new Student("小丽", 88));
        assertEquals(4, manager.all().size());
    }

    @Test
    @DisplayName("删除:删存在的返回 true,数量减少")
    void remove_存在() {
        assertTrue(manager.remove("小明"));
        assertEquals(2, manager.all().size());
    }

    @Test
    @DisplayName("删除:删不存在的返回 false,数量不变")
    void remove_不存在() {
        assertFalse(manager.remove("不存在"));
        assertEquals(3, manager.all().size());
    }

    @Test
    @DisplayName("修改成绩:存在的学生改成功")
    void updateScore_存在() {
        assertTrue(manager.updateScore("小红", 60));
        // 验证改动确实生效:把小红从 58 改成 60 后,再排序找出来核对分数
        double hongScore = 0;
        for (Student s : manager.all()) {
            if (s.getName().equals("小红")) hongScore = s.getScore();
        }
        assertEquals(60, hongScore, 0.001);
    }

    @Test
    @DisplayName("平均分:三个学生 92/58/76 平均 75.33")
    void average_三个学生() {
        assertEquals(75.333, manager.average(), 0.001);
    }

    @Test
    @DisplayName("平均分:空列表返回 0")
    void average_空列表() {
        assertEquals(0.0, new StudentManager().average(), 0.001);
    }

    @Test
    @DisplayName("最高分与最低分")
    void maxAndMin() {
        assertEquals(92, manager.max(), 0.001);
        assertEquals(58, manager.min(), 0.001);
    }

    @Test
    @DisplayName("排序:降序排列,第一是最高分")
    void sorted_降序() {
        assertEquals("小明", manager.sorted().get(0).getName());
    }
}
```

(补充:上面 `updateScore_存在` 没有用现成的"按名字查"方法,而是手写 `for` 找出来再断言成绩,说明 `StudentManager` 缺一个 `findByName(name)` 这类查询入口.测试往往会反过来逼你改进类设计:加一个 `findByName` 返回 `Student`(或第 17 期的 `Optional<Student>`),测试就能写得 `assertEquals(60, manager.findByName("小红").orElseThrow().getScore(), 0.001)` .你可以试着重构 `StudentManager` 让测试更顺.)

跑完后做一件事:**故意改坏逻辑** ![:tieba_095:](img/05b2136fa15e9c3e0fd5ed014b3c6247.png) 把 `StudentManager.average()` 里的 `/ students.size()` 删掉,再跑测试,看 `average_三个学生` 变红,其他测试不受影响.这就是"测试把错误锁在了笼子里".

第 12 期我们运行 main 程序,手动输入选项一个个功能点过去.那是"人肉测试".今天同样的功能,几十行测试代码,一键全跑.第 12 期结尾我们问"还有什么边界要防",测试就是防边界的最佳工具:空列表、删不存在的名字,今天全写进测试了.以后还会见到 Spring Boot 的接口测试(MockMvc),套路一模一样:先写"应该是什么样",再让代码去满足.

**总结**

本期把"验证"变成了代码:

- **为什么测**:改代码不怕改坏、测试是活的文档

- **JUnit 5**:`@Test` 标记测试方法,IDEA/构建工具一键跑

- **断言**:`assertEquals`/`assertTrue`/`assertNotNull`/`assertThrows`;浮点比较要带误差

- **生命周期**:`@BeforeEach` 每个测试前重建环境,测试互不污染

- **好习惯**:一个测试一个行为,测边界和异常

- 给第 12 期 StudentManager 写全套测试,跑绿再改坏逻辑看它变红
