# Java开发教程28-抽象工厂模式

本期是Java开发教程系列的第二十八期,设计模式专题第二期,讲**抽象工厂模式**:工厂方法管"一种产品的制造",它管"一整套产品的成套交付".适合"产品一族必须搭配着用"的场景,比如 UI 主题:一套主题的按钮、输入框、背景色要长得协调,不能按钮是深色的、背景是浅色的.若你已经理解抽象工厂与工厂方法的区别,可以跳过本期内容.

**一、新问题:产品开始"成套"出现**
上一期的日志系统,产品只有一种(Logger),工厂方法够用.但假设现在做的是 UI 框架,要支持**主题换肤**:
- 按钮(Button)
- 输入框(TextField)
- 背景色(Background)
关键约束:**同一主题的组件必须成套**.深色主题的按钮+深色输入框+深色背景,不能深色按钮配浅色输入框,不然界面就花了.
如果用工厂方法(每种产品一个工厂):
```
// 需要 6 个工厂!
DarkButtonFactory      // 深色按钮
LightButtonFactory     // 浅色按钮
DarkTextFieldFactory   // 深色输入框
LightTextFieldFactory  // 浅色输入框
DarkBackgroundFactory  // 深色背景
LightBackgroundFactory // 浅色背景
```
问题很明显:**"主题"这个整体概念被拆碎了**:换主题要同时换三个工厂,漏换一个就是混搭事故.而且每加一种组件(比如复选框),就要给每个主题各加一个工厂,工厂数量跟着主题×组件数量膨胀.
直觉告诉我们:**"深色"和"浅色"才是组团单位,组件是组里的成员**.把"组"当成工厂的维度:这就是抽象工厂.
---
**二、抽象工厂:工厂也分层**
抽象工厂的结构,把上一期的"产品接口"换成"产品族接口":
```
// 产品接口:每种产品一套
public interface Button {
    void render();
}

public interface TextField {
    void render();
}

// 抽象工厂:一个"主题",负责生产整套组件
public interface UIFactory {
    Button createButton();
    TextField createTextField();
}

// 具体工厂:每个主题一个,成套生产
public class DarkUIFactory implements UIFactory {
    @Override
    public Button createButton() {
        return new DarkButton();        // 深色按钮
    }

    @Override
    public TextField createTextField() {
        return new DarkTextField();     // 深色输入框
    }
}

public class LightUIFactory implements UIFactory {
    @Override
    public Button createButton() {
        return new LightButton();
    }

    @Override
    public TextField createTextField() {
        return new LightTextField();
    }
}
```
具体产品类(每个都要实现对应接口):
```
public class DarkButton implements Button {
    @Override
    public void render() {
        System.out.println("深色按钮");
    }
}

public class LightButton implements Button {
    @Override
    public void render() {
        System.out.println("浅色按钮");
    }
}

public class DarkTextField implements TextField {
    @Override
    public void render() {
        System.out.println("深色输入框");
    }
}

public class LightTextField implements TextField {
    @Override
    public void render() {
        System.out.println("浅色输入框");
    }
}
```
业务代码(渲染一整个界面)只依赖抽象工厂:
```
public class UIApp {
    private UIFactory factory;   // 只认抽象工厂

    public UIApp(UIFactory factory) {
        this.factory = factory;
    }

    public void renderAll() {
        Button button = factory.createButton();      // 成套:同一个工厂出来的
        TextField field = factory.createTextField();
        button.render();
        field.render();
    }
}

// 换主题 = 换一个工厂对象,界面整组换装
UIApp app = new UIApp(new DarkUIFactory());
app.renderAll();
```
核心收获:**factory.createButton() 和 factory.createTextField() 保证出自同一个主题**."成套"由"同一个工厂"天然保证,想混搭都难.换主题只动一处(`new DarkUIFactory()` → `new LightUIFactory()`),全套组件跟着换.

**三、抽象工厂 vs 工厂方法:一张表说清**
| 维度 | 工厂方法 | 抽象工厂 |
| --- | --- | --- |
| 管什么 | **一种**产品的制造 | **一族**相关产品的成套制造 |
| 产品关系 | 各自独立 | 必须搭配使用 |
| 扩展新产品(组件) | 加一个工厂 | 每个主题工厂都要加方法(难) |
| 扩展新族群(主题) | 加一个工厂(易) | 加一个工厂(易) |
| 关系 | — | 抽象工厂内部**通常用工厂方法实现**(每个 createXxx 就是一个小工厂) |
一句话:**工厂方法管"纵向"(一种产品越做越多),抽象工厂管"横向"(一族产品成套交付)**.它们不矛盾.抽象工厂的每个 `createButton()`,内部往往就是一段工厂方法逻辑.
**各自的扩展痛点**也要记住:抽象工厂加"新产品"(比如加复选框组件),所有主题工厂都要改,这是它的固有代价;所以抽象工厂适合**产品族稳定、族很多**的场景.相反,产品族少但产品种类会膨胀,工厂方法更合适.
---
**四、什么时候用,什么时候别用**
**用抽象工厂**:
- 有明确的"产品族"(主题、平台、数据库类型),且族内产品必须搭配
- 产品族会不断新增(新主题随时来),但族内产品种类稳定

**别用抽象工厂**:
- 产品之间没有"成套"约束.各自独立的日志、各自的工具类,用工厂方法或直接 new
- 产品种类会频繁增加.每加一种,所有族都要改,痛苦翻倍
新手最容易犯的错:把"有多个工厂类"当成"抽象工厂".判据是**“成套性”**:你的产品需要配套使用吗?不需要,那就是工厂方法.

**五、源码:哪里见过它**
**Java AWT 的 Toolkit** 是教科书级例子:同一套 API,在 Windows 上 `Toolkit.getDefaultToolkit()` 返回 Windows 平台实现,在 Linux 上返回对应实现.“平台"就是族,窗体、按钮、图形是族内产品,一套平台实现整套控件.**以后你会再见它**(先留个印象,现在不用懂):到了数据库阶段(第 72 期 JDBC),每个数据库驱动的连接、语句对象都是一族产品,换数据库 = 换一整族;到了 Spring 阶段,自动配置本质也是"按环境选一套 Bean”.等学到那里,再回来对照今天的"成套交付"思想.
还有一个藏在日常里的例子:**第 13 期的模组加载器**:NeoForge 和 Fabric 是两套"族":各自的注册 API、各自的事件系统,族内自洽、族间不兼容,正是抽象工厂"成套交付"的活案例(虽然它们的 API 设计没严格用这个模式,但思想同源).

**六、小项目:UI 组件主题工厂**
动手实现上面的完整示例,并加一个"组件"扩展自己体验:加第三种产品 `Checkbox`(复选框),每个主题补一个 `createCheckbox`.你会真切体会到抽象工厂"加新产品难、加新族容易"的滋味.
文件 `Main.java`:
```
public class Main {
    public static void main(String[] args) {
        // 换主题只换这一行
        UIFactory factory = new DarkUIFactory();

        // 业务代码只认接口,不知道也不关心具体是什么主题
        Button button = factory.createButton();
        TextField field = factory.createTextField();
        button.render();
        field.render();
    }
}
```
(接口与类按第二节的代码补齐:`Button`/`TextField` 两个接口,`UIFactory` 抽象工厂,`DarkUIFactory`/`LightUIFactory` 两个具体工厂,四个具体产品类.)
扩展练习:
1. 加 `Checkbox` 产品:接口 + 深/浅两个实现 + 两个工厂各加 `createCheckbox()`.注意**旧工厂都被改了**,这就是抽象工厂的固有代价
2. 加一个 `BlueUIFactory` 新主题:三个组件 + 一个工厂.**一行旧代码没动**,这就是抽象工厂的拿手好戏
3. 两个练习做完对比一下,把"加产品难、加族易"的体会写下来,面试问区别时这就是你的答案

**朝花夕拾:第 13 期"选加载器"时的纠结**
第 13 期选模组加载器,我们纠结 NeoForge 还是 Fabric:今天回头看,那其实是在选"产品族":选定一家,物品注册、事件监听、配置 API 全是这一族的,混着用两族的 API 会Boom.抽象工厂解决的就是这种"选族"问题:**选定一个族,整套配套交付,不会拼出四不像**.现在你能说出"为什么不能 NeoForge 注册物品、Fabric 监听事件"的理论答案了:因为它们不是同一个族.

**总结**
本期学会了让"成套产品"乖乖配套:
- **新问题**:产品成套出现,工厂方法会把"族"拆碎,换主题像拆炸弹
- **抽象工厂**:工厂分"族",一个工厂生产整套;成套性由"同一个工厂"保证
- **vs 工厂方法**:一种产品 vs 一族产品;加产品难、加族易,与工厂方法互补
- **场景判断**:有配套约束才用,没有就别套
- **源码**:AWT Toolkit 按平台出整套实现- UI 主题工厂小项目,亲手体会"加产品/加族"的差别
