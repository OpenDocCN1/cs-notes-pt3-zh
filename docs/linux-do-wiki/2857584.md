# Java开发教程29-单例模式

本期是Java开发教程系列的第二十九期,设计模式专题第三期,讲**单例模式**——整个程序里某个类只允许存在一个实例.它是 23 种模式里最常用、写法最多、面试最常考的一个:配置管理器、线程池、连接池,全是单例.若你已经掌握饿汉/懒汉/双检锁等写法及各自优劣,可以跳过本期内容.
**每期叠甲**:
时间仓促,水平有限,文中难免存在缺点和错误,恳请广大开发者和从业者指正.
---
**一、需求:为什么只要一个实例**
回想第 20 期的 `GameConfig`:它读配置文件,全程序各处都要查配置.问题:如果每个地方都 `new GameConfig()` 一个,每个对象各自读一遍文件,配置存着多份拷贝,改了一处另一处不知道,纯粹浪费内存和 IO.
更好的设计:**整个程序只允许有一个 GameConfig 实例**,谁要用都拿这同一个,这就是单例.
什么样的对象适合单例?标准是"**全局只需一份,且多份有害或浪费**":
- 配置管理器(多份 = 数据不同步)
- 线程池(第 19 期:多份 = 线程资源翻倍)
- 连接池(多份 = 数据库连接爆炸)
- 全局日志器、随机数生成器等"无状态工具"(多份无害,但一份就够了)
单例模式就是回答一个问题:**怎么保证一个类只能有一个实例,并全局都能拿到它?** 两个关键动作:
1. **挡住 new**:构造器设为 `private`,外面想 `new` 都编译不过去
2. **提供唯一入口**:类自己留一个 `getInstance()` 静态方法,返回那唯一的一个
---
**二、写法演进(一):饿汉式**
最简单:类加载时就把实例建好(饿汉 = 饿得等不及,一加载就吃  ![:shortcake:](https://cdn.ldstatic.com/images/emoji/twemoji/shortcake.png?v=15)  是啊,吃什么?):
```
public class GameConfig {
    private static final GameConfig INSTANCE = new GameConfig();   // 类加载即建

    private GameConfig() { }       // 构造器私有,外面 new 不了

    public static GameConfig getInstance() {
        return INSTANCE;           // 永远返回同一个
    }
}
```
- 优点:**简单、线程安全**.`static final` 字段由类加载机制保证只初始化一次,多线程随便调 `getInstance` 也不会出两个实例
- 缺点:类一加载就建,哪怕程序从头到尾没用过它也白建(叫"急加载")

新手第一版就该写饿汉式:**简单不出错**,"懒"是优化,不是义务.
---
**三、写法演进(二):懒汉式与它的坑**
想省掉"没用也建"的浪费,改成**第一次调用时才建**(懒汉 = 懒,用到才动手):
```
public class GameConfig {
    private static GameConfig instance;      // 注意:不是 final 了

    private GameConfig() { }

    public static synchronized GameConfig getInstance() {   // 加了锁
        if (instance == null) {
            instance = new GameConfig();
        }
        return instance;
    }
}
```
`getInstance` 加了 `synchronized`(第 19 期):不加会怎样?两个线程同时发现 `instance == null`,各自 `new` 一个,单例破了.加锁后安全了,但问题也来了:**每次调用都要走锁**,而 `getInstance()` 是高频操作(每处查配置都调),锁的开销白白浪费.毕竟初始化只发生一次,之后全是读.
这就是经典的"懒 + 快"矛盾:又想要懒加载,又不想每次加锁.
---
**四、写法演进(三):双检锁**
**双重检查锁定(Double-Checked Locking)**:先不加锁查一次,大概率直接返回;只有第一次(instance 还是 null)才进锁,锁里再查一次确认:
```
public class GameConfig {
    private static volatile GameConfig instance;   // volatile 为什么必要?看下面

    private GameConfig() { }

    public static GameConfig getInstance() {
        if (instance == null) {                    // 第一次检查:不加锁,多数情况直接过
            synchronized (GameConfig.class) {
                if (instance == null) {            // 第二次检查:锁里再确认
                    instance = new GameConfig();
                }
            }
        }
        return instance;
    }
}
```
三个关键点逐个说:
1. **两次判空**:第一次拦截绝大多数调用(不用加锁);第二次防止"两个线程同时第一次进来"的竞争,A 在锁里建完,B 进来后看到非 null,直接跳过
2. **volatile 为什么必须加?** 第 19 期学过 volatile 管可见性;这里还有一层:`instance = new GameConfig()` 在底层是三步,分配内存、调用构造器、把引用赋给 instance.**编译器可能重排**这两步(先赋引用、后调构造器),另一个线程就能在"引用已赋值但构造器没跑完"时拿到一个**半初始化对象**.`volatile` 禁止这种重排,保证"引用可见时对象一定完整".删掉它,单例在极端并发下可能给出半个对象,面试问"双检锁为什么 volatile",答案就是这句
3. 锁对象是 `GameConfig.class`.静态方法里没有 `this`,锁类对象

双检锁是"懒 + 快"的最优解之一,也是面试手写频率最高的版本.

**五、写法演进(四):静态内部类与枚举**
**静态内部类版**:利用"类只有被用到时才加载"的机制,天然实现懒加载 + 线程安全:
```
public class GameConfig {
    private GameConfig() { }

    private static class Holder {                 // 内部类,用到时才加载
        private static final GameConfig INSTANCE = new GameConfig();
    }

    public static GameConfig getInstance() {
        return Holder.INSTANCE;                   // 第一次调用才触发 Holder 加载
    }
}
```
- 第一次调 `getInstance()` 时,JVM 才加载 `Holder` 类,才执行 `new`: **懒加载**
- 类加载是线程安全的(JVM 保证一个类只初始化一次),**不用锁**
- 没有 volatile、没有两次判空,代码最干净.很多老手的最爱

**枚举版**:最简,并且**免疫反射和序列化破坏**:
```
public enum GameConfig {
    INSTANCE;                    // 单例就是枚举的一个值

    private int volume = 80;

    public int getVolume() { return volume; }
    public void setVolume(int v) { this.volume = v; }
}

// 使用:GameConfig.INSTANCE.getVolume()
```
前面所有写法,理论上都能被两种手段破坏:
- **反射**:`setAccessible(true)` 强行调私有构造器,再 new 一个
- **序列化**:第 21 期反序列化时 `readObject` 会再造一个实例

枚举天生免疫两者(枚举实例由 JVM 保证唯一,反射和序列化都有保护),还最简.缺点:枚举语义上"不像是类"、有些框架对枚举支持差,但就单例本身而言,它是**终结者**写法.

**六、什么时候用,什么时候别用**
**用单例**:
- 全局只有一份且多份有害:配置、线程池、连接池、缓存
- 工具类本身无状态、被各处调用:随机数、日期格式化器(其实静态方法也能干,单例是"要对象状态"时的选择)
**别用单例**:
- 对象有**实例状态**且不同场景要不同配置:比如一个模拟器要两个独立世界,硬单例就堵死了
- 团队项目里过度单例 = 全局变量,测试时想换 mock 实现都难(依赖注入是更现代的替代,Spring 会看到)
提醒:**单例是"多份有害"时的最后手段,不是"懒得传对象"的借口**.

**七、JDK 里的单例影子**
单例不是只能自己写,JDK 里早就藏了两处"唯一实例"的思想,理解它们能帮你把模式认进实际代码:
- **Runtime.getRuntime()**:`Runtime` 类代表"Java 运行环境",一个 JVM 进程只有一份,所以它本身就是单例.构造器是私有的,对外靠 `Runtime.getRuntime()` 拿那唯一一个实例.这正是饿汉式(类加载即建,`static final`).
- **Integer.valueOf(int) 缓存**:`Integer.valueOf(127)` 两次返回的是**同一个对象**:JDK 把 -128~127 的 `Integer` 在类加载时预先建好放进缓存数组,谁要这个区间的值都复用同一个对象.严格说它不是"一个类一个实例",而是"一族小对象各建一份并复用",思想同源:能复用就不重复造.这其实是享元(第 37 期)的味道,但"全局只有一组缓存的 Integer 对象"和单例"全局只有一份"是同一种"少造对象"的思路.
所以面试被问"JDK 里有哪些单例",答 `Runtime.getRuntime()` 打头准没错,再补一句 `Integer` 缓存体现的"唯一实例思想",就能看出你把模式和源码挂上了钩.

**八、小项目:配置管理器单例化**
把第 20 期的 `GameConfig` 改造成双检锁单例(顺带复习双检锁),再全局共用:
文件 `GameConfig.java`:
```
import java.io.File;
import java.io.FileReader;
import java.io.FileWriter;
import java.nio.charset.StandardCharsets;
import java.util.Properties;

public class GameConfig {
    private static volatile GameConfig instance;

    private final File file = new File("game.properties");
    private Properties props = new Properties();

    private GameConfig() {                    // 构造器私有:外部 new 不了
        if (file.exists()) {
            try (FileReader reader = new FileReader(file, StandardCharsets.UTF_8)) {
                props.load(reader);
            } catch (Exception e) {
                System.out.println("读取配置失败,使用默认配置");
            }
        }
    }

    public static GameConfig getInstance() {  // 双检锁
        if (instance == null) {
            synchronized (GameConfig.class) {
                if (instance == null) {
                    instance = new GameConfig();
                }
            }
        }
        return instance;
    }

    public int getVolume() {
        return Integer.parseInt(props.getProperty("volume", "80"));
    }

    public void setVolume(int volume) {
        props.setProperty("volume", String.valueOf(volume));
        try (FileWriter writer = new FileWriter(file, StandardCharsets.UTF_8)) {
            props.store(writer, "game config");
        } catch (Exception e) {
            System.out.println("保存失败");
        }
    }
}
```
文件 `Main.java`:
```
public class Main {
    public static void main(String[] args) {
        // 三个地方同时拿配置,拿到的必须是同一个对象
        GameConfig a = GameConfig.getInstance();
        GameConfig b = GameConfig.getInstance();
        System.out.println("是同一个对象吗: " + (a == b));   // true

        a.setVolume(90);
        System.out.println("b 看到的最新音量: " + b.getVolume());   // 90,数据共享
    }
}
```
动手练习:把构造器上的 `private` 改成 `public`,编译报错:体会"挡住 new"是单例的第一道防线;再把 `getInstance` 里两次判空都删掉换成简单懒汉,想想为什么并发下会破.

**朝花夕拾:第 19 期线程池的"全局唯一"**
第 19 期我们学线程池,`Executors.newFixedThreadPool` 每调一次就建一个新池子.当时没说,线程池**通常也应该只建一个**:全程序共享一个线程池,线程复用率最高、总线程数可控;每个模块各自建池,线程数直接翻倍浪费.所以真实项目里,"全局唯一线程池"就是单例的经典用例(但也会有特殊情况).

**总结**
本期把"唯一"变成了一种模式:
- **单例的骨架**:构造器私有 + 静态 `getInstance()`
- **四种写法演进**:饿汉(简单安全)/ 懒汉 synchronized(安全但每次加锁)/ 双检锁(volatile 防重排)/ 静态内部类(懒 + 无锁干净);枚举是终结者
- **双检锁三要素**:两次判空、synchronized、volatile 禁重排
- **场景判断**:多份有害才用;别拿单例当"懒得传参"的借口
- 配置管理器单例化小项目
