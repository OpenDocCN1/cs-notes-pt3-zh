# MCP：让 模型\用户\软件 决定 调用 API 获取辅助信息



现在的一些工作 聚焦于 如何 高效的向 ai 的消息流中 增加 详细充分的信息 来辅助 模型的思考。不论是 cursor、cline 还是现在我们谈论的 MCP（Model Context Protocol）服务。

> 事实上 MCP 是指协议，但是我们在使用中谈论到 MCP 特指 MCP 服务，在不引起歧义的情况下，本文以 MCP 代替。

MCP 能够提供的信息 可以分为三种：Resource（软件控制）、Tool（模型控制）、Promot（用户控制）。具体来说，MCP 能够：

> Expose data through **Resources** (think of these sort of like GET endpoints; they are used to load information into the LLM’s context)

>

> 通过资源暴露数据（可以将这些资源想象成 GET 端点；它们用于将信息加载到 LLM 的情境中）

> Provide functionality through **Tools** (sort of like POST endpoints; they are used to execute code or otherwise produce a side effect)

>

> 通过工具提供功能（可以将这些工具想象成 POST 端点；它们用于执行代码或其他产生副作用的操作）

> Define interaction patterns through **Prompts** (reusable templates for LLM interactions)

>

> 通过提示定义交互模式（LLM 交互的可重用模板）

> And more!

>

> 摘自 MCP sdk README

首先我们解释 提到 的 **GET 和 POST** 的比喻。下面给一个 Tool 类型的 MCP 在使用中的 具体情况，就能理解：当开启了 mcp，以cherry为例 会有 三个 请求。

第三次请求：

![8ab28b482c593e28b4d27030e2823d31478×1391 179 KB](https://cdn3.ldstatic.com/original/4X/b/2/1/b21bf807d8a10af6144be42b26b556c1ada21ed9.png)

第一个请求 把 问题 和 能够使用的api以及api的参数api的解释 发给 模型端，返回的是模型端根据问题选择的api以及参数。第二个请求 会 根据第一次的请求结果中的参数 和 api 发送给 mcp服务器，请求到 辅助 内容。第三次 再将 辅助内容+使用的api服务+问题（上下文）【不同的 role： user、assistant、tool】 一起 发给 模型端，然后得到 最后的结果。那么这里的 POST指的是，**用户端 将 问题发给模型，模型返回MCP的调用方法，然后本地进行调用MCP**。

对于Resource，这里的调用是按照你使用的软件设定的方式，不需要请求LLM来回调参数，基本上就是本地的文档图片等的调用。那么对于Prompt，事实上相当于Prompt的模板由用户针对特定任务设定，这样可以方便的标准化的和模型交互特定任务。

一般来说，现在有的MCP都是担任的Tool服务，因为这里涉及到了**第三方API的调用**
