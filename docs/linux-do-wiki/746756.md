>     ✿ RAII与智能指针
---
C++没有垃圾自动回收机制，程序员需要时刻注意资源的释放。
除了**忘记释放**，资源还可能会因为**错误终止**（指非强制终止）导致资源泄露。
而对象会在其**生命周期结束**和**错误终止时**（指非强制终止）自动调用析构函数。
基于这样的特性，Bjarne提出了RAII"资源获取即初始化"的思想。
---
# ◢ RAII
> 构造中获得，析构中释放
- 获得：资源在对象构造时**传入**，或者直接在对象的**构造中申请**资源。
- 释放：将资源的释放写在析构中。
通过RAII可以确保资源的正确释放。
## ❖ 资源独占要求
RAII将资源和对象生命周期绑定。
如果允许赋值或复制，就会出现一个资源绑定到多个生命周期上的情况。

独占式RAII不允许**直接**复制和赋值。
## ❖ 最佳实践
- 成对 `acquire/release` 的资源都应交给 RAII 对象负责。
- 对象创建在**尽可能小的作用域**中。

使得可见代码少，异常可能也小。
让析构尽快执行。
# ◢ 智能指针
C++中的RAII落地。
**作用**：可以用于托管资源，并对资源的复制赋值进行专门管理。
根据对资源独占要求作出以下分类：
| 类型 | 资源占有 | 特点 |
| --- | --- | --- |
| unique_ptr | 独占 | 禁止复制，可以移动 |
| shared_ptr | 共享 | 允许复制，可以移动 |
| weak_ptr | 仅观察 | 允许复制，可以移动 |
## ❖ unique_ptr
上面提到，**禁复制，能移动**。

即`unique_ptr`作为函数形参时只能传入右值：
```
struct C{};
void fun(std::unique_ptr<C> p);

// 使用
fun(p); // 左值error
fun(std::move(p));  // 右值ok
fun(std::unique_ptr<C>());  // 右值ok
```
## ❖ shared_ptr
能复制，能移动。
这里的复制并**不是拷贝资源本身**，

而是复制**指向资源的指针**与**控制块指针**（维护引用数等信息）。
每次拷贝则引用计数+1，释放则-1，释放后如果计数归零才会释放资源。
```
shared_ptr<int> sp(new int(10));  // 引用计数为1
auto sp2 = sp;  // 引用计数为2
```
---
shared_ptr对象之间如果相互引用（或多对象成环引用），那么它们都会等待对方的释放才释放，形成**循环引用**，导致资源泄露。
C++引入weak_ptr解决这个问题。
## ❖ weak_ptr
`weak_ptr`会在控制块中添加一个弱引用计数，决定控制块的生存周期。
| 事件 | 效果 |
| --- | --- |
| 强引用计数归零 | 释放资源 |
| 强引用+弱引用计数归零 | 释放控制块 |
将循环强引用的双方改为弱引用就不会影响资源的释放。
控制块保留可以给`weak_ptr`判断资源是否还有效（使用expired方法）。
```
shared_ptr<int> sp(new int(10));
weak_ptr<int> wp(sp);

if(wp.expired()){
    // 验证有效后操作
}
```
弱引用的资源需要升格出一个强引用（使用lock方法）来进行访问。
```
shared_ptr<int> sp2 = wp.lock();
if(sp2){
    // 提升后操作
}
```
## ❖ 自定义删除器
`shared_ptr`和`unique_ptr`都是调用默认的`delete`进行资源释放，但不是所有的资源都能这么释放的（例如文件需要`fclose()`）。
因此我们需要自定义删除器，传入删除器的方式如下：
| 类型 | 方式 |
| --- | --- |
| unique_ptr | 模板实例化时指定 |
| shared_ptr | 作为参数传入 |
| weak_ptr | 不持有资源，无需释放 |
```
struct FILECloser{
  void operator()(FILE * fp){
     fclose(fp);
  }
};

unique_ptr<FILE，FILECloser> up(fopen("test.txt","a+"));
shared_ptr<FILE> sp(fopen("test.txt","a+"),FILECloser{});
```
unique追求零开销，放模板能优化占用内存小。

shared本身就需要内存维护控制块，不追求零开销，转而使用参数传入来增强灵活性。
## ❖ 最佳实践
- 尽量使用智能指针来管理动态内存，**避免裸指针管理**。
- 禁止一个裸指针托管给多个智能指针。
- new表达式和智能指针构造分开写。
| 类型 | 使用建议 |
| --- | --- |
| unique_ptr | 优先使用 |
| shared_ptr | 仅当需要共享管理 |
| weak_ptr | 仅当shared_ptr有循环引用问题 |
## ❖ 智能指针工厂函数
上面我们提到
> new表达式和智能指针构造分开写
是因为在如下环境中：
```
f(std::shared_ptr<Foo>(new Foo), g());
```
`f`函数接收智能指针和`g()`返回结果。
参数会**先实参求值，才会生成临时对象赋值到形参**。

即先计算`new Foo`和`g()`且[顺序不定](https://linux.do/t/topic/746756/2)，然后才会生成`shared_ptr`临时对象。
如果在执行`new Foo`后`g()`报错，那么不会生成临时对象，裸指针将不会被智能指针接管，导致泄露。
---
为了解决上述问题，C++11提供了`make_shared`智能指针工厂函数：
- 裸指针的构建在内部进行，**出错则释放**。
- 控制块和资源的堆分配一起进行，减少碎片和开销。
```
std::shared_ptr<Foo>(new Foo(args));  // 旧用法
auto p = std::make_shared<Foo>(args); // 工厂函数用法
```
---
`unique_ptr`虽然没有控制块分配优化的需要，但对裸指针安全构建还是有需求的。

C++14也为其引入了`make_unique`工厂函数。
## ❖ this指针的返回
上面我们提到
> 禁止一个裸指针托管给多个智能指针
在类成员函数返回this指针时是这个误用的高发区。
---
例如:
```
Data * add(Data * d){
    this->val += d->val;  // 值相加
    return this;  // 返回加值后的对象
}
```
如果在下述场景中使用：
```
shared_ptr<Data> d1(new Data(1));
shared_ptr<Data> d2(new Data(2));

shared_ptr<Data> d3(d2->add(d1.get()));
// 此时相当于d2,d3均管理new Data(2)的裸指针
```
---
如果改进为
```
shared_ptr<Data> add(Data * d){
    this->val += d->val;
    return shared_ptr<Data>(this);  // 返回共享智能指针
}
```
那实际上还是多智能指针托管同一个裸指针：
- d2智能指针
- d2的add函数返回的临时智能指针
这会造成两次析构释放同一个裸指针，也不可取。
---
C++引入`enable_shared_from_this`类，继承后调用`shared_from_this()`即可得到一个共享的封装了同一this的`shared_ptr`，即**共享指针的共享**。
```
class Data
: public std::enable_shared_from_this<Data> // 第一步：继承
{
public:
  shared_ptr<Data> add(Data * d){
      this->val += d->val;
      return shared_from_this(); // 第二步：返回共享this的shared智能指针
  }
};
```
