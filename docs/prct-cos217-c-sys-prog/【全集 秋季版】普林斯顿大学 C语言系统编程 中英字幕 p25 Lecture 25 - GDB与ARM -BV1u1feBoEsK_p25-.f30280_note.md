# C语言系统编程：25：GDB与ARM调试实战

在本节课中，我们将学习如何使用GDB调试器来调试混合了C语言和ARM汇编语言的程序。我们将通过一个具体的例子，即一个自定义的字符串长度计算函数 `Sterlin`，来演示GDB在汇编层面的核心调试技巧，包括检查寄存器、内存、设置断点与观察点等。这些技能对于完成课程作业5和6至关重要。

## 程序结构概述

我们的示例程序包含C语言驱动代码和ARM汇编代码。C代码 (`main`) 负责分配并初始化一个字符串，然后调用我们手写的汇编函数 `Sterlin` 来计算其长度。汇编函数 `Sterlin` 实现了遍历字符串直到遇见空字符（`\0`）的算法。

以下是 `Sterlin` 函数的初始汇编实现核心逻辑：

```assembly
Sterlin:
    // 序言：设置栈帧
    sub sp, sp, #minstack
    str x30, [sp]
    str xzr, [sp, #I]        // 将索引变量 I 初始化为 0 并存入内存

    ldrb w2, [x0]            // 加载字符串的第一个字节到 w2
loop:
    cmp w2, wzr              // 比较当前字符是否为 0
    b.eq end                 // 如果是，跳转到结束

    ldr x1, [sp, #I]         // 从内存加载索引 I 到 x1
    add x1, x1, #1           // 索引 I++
    str x1, [sp, #I]         // 将更新后的索引存回内存

    add x1, x0, x1           // 计算当前字符地址: 基地址 x0 + 索引 x1
    ldrb w2, [x1]            // 加载当前字符到 w2
    b loop                   // 无条件跳回循环开始

end:
    ldr x0, [sp, #I]         // 将最终索引（即字符串长度）放入返回值寄存器 x0
    // 收尾：恢复栈帧并返回
    ldr x30, [sp]
    add sp, sp, #minstack
    ret
```

上一节我们介绍了程序的基本结构，本节中我们将使用GDB一步步探索其运行状态。

## 启动GDB并设置初始断点

首先，我们编译程序并使用GDB启动它，并在 `Sterlin` 函数入口处设置断点。

```bash
gdb ./program
(gdb) break Sterlin
(gdb) run
```
程序运行后会等待用户输入字符串大小。输入一个数字（例如10）后，GDB会在 `Sterlin` 函数的第一条指令处暂停。

## 检查寄存器状态

在汇编层面，变量主要存储在寄存器和内存中。我们可以使用 `info registers` 命令查看所有寄存器的当前值。

```bash
(gdb) info registers
```
这将显示 `x0`, `x1`, `x2` 等通用寄存器以及 `sp` (栈指针)、`pc` (程序计数器) 的值。例如，`x0` 应包含传入的字符串地址。

要单独查看某个寄存器的值，需要在寄存器名前加 `$`。

```bash
(gdb) print /x $sp  # 以十六进制打印栈指针的值
(gdb) print /x $pc  # 以十六进制打印程序计数器的值
```

执行一条指令（`stepi`）后，再次打印 `$sp`，可以看到栈指针的变化，这验证了序言中分配栈空间的操作。

## 检查内存内容

我们可以使用 `x`（examine）命令来检查特定内存地址的内容。格式为 `x/[数量][格式][单位] 地址`。

例如，在存储了链接寄存器 `x30` 之后，我们可以检查栈顶的内容：
```bash
(gdb) x /1xg $sp      # 以8字节(G)十六进制(x)格式，查看sp指向的1个单位数据
```
为了理解这个地址的含义，我们可以用 `/a` 格式将其解释为一个代码地址：
```bash
(gdb) x /1a $sp
```
输出可能显示为 `main+96`，表明这是 `main` 函数中调用 `Sterlin` 之后的下一条指令地址，符合预期。

同样，我们可以查看即将执行的下一条指令：
```bash
(gdb) x /1i $pc
```

## 使用`display`持续监控

在循环调试中，反复打印某些值很繁琐。`display` 命令可以自动在每次程序暂停时显示指定表达式。

以下是设置持续监控的例子：
```bash
(gdb) display /x $w2          # 以十六进制持续显示寄存器 w2 的值
(gdb) display /c $w2          # 以字符格式持续显示 w2 的值
(gdb) display /x $x1          # 以十六进制持续显示寄存器 x1 的值
```
对于内存位置，我们需要进行类型转换来模拟解引用：
```bash
(gdb) display *(unsigned long*)($sp + 8)  # 持续显示栈上偏移8字节处的值（即变量I）
```

## 控制程序执行与高级断点

简单地单步执行（`stepi`）在长循环中效率很低。GDB提供了更强大的控制流命令。

**1. 执行多步：**
```bash
(gdb) stepi 7  # 一次性执行7条指令
```

**2. 设置观察点（Watchpoint）：**
如果我们想监控某个寄存器或变量的**值何时改变**，可以使用观察点。这对于检测循环何时遇到空字符非常有用。
```bash
(gdb) watch $w2  # 当 w2 的值改变时暂停
(gdb) continue    # 继续执行，直到 w2 改变
```
当 `w2` 从字符 `'A'` 的ASCII码97变为0时，GDB会暂停，并显示旧值和新值。

**3. 设置条件断点：**
我们可以在特定行设置断点，并附加条件，使其仅在条件满足时触发。
```bash
(gdb) break 19 if $w2 == 0  # 在源代码第19行设置断点，仅当 w2 等于 0 时触发
(gdb) continue
```
这样，程序会一直运行，直到在指定行遇到空字符时才暂停。

**4. 带次数的继续：**
如果知道循环大概次数，可以命令GDB忽略断点若干次。
```bash
(gdb) continue 100  # 继续运行，直到第100次遇到活动断点时再暂停
```

## 性能优化实战

调试的最终目的不仅是修复错误，也包括理解性能瓶颈。我们的初始 `Sterlin` 实现为了清晰，大量使用了内存访问，效率不高。让我们尝试优化。

**优化1：使用寄存器代替内存**
将循环索引 `I` 从内存移到寄存器 `x1` 中，并直接用 `x1` 作为指针遍历字符串，避免反复计算地址。
```assembly
Sterlin:
    mov x1, x0               // x1 作为当前字符指针，初始化为字符串起始地址
loop:
    ldrb w2, [x1], #1        // 从x1加载字节到w2，然后x1自增1（后变址寻址）
    cbz w2, end              // 如果 w2 为 0，跳转到 end
    b loop
end:
    sub x0, x1, x0           // 计算长度：当前指针 - 起始指针
    sub x0, x0, #1           // 调整长度（因为指针已越过空字符）
    ret
```
**优化2：移除不必要的栈操作**
由于函数内部没有调用其他函数，我们可以省略栈帧的设置和恢复，进一步减少开销。
**优化3：优化循环结构**
将 `while` 循环改为 `do-while` 结构，确保至少执行一次比较，并将条件判断置于循环尾部，减少一次分支跳转。

每次修改后，我们都应重新计时。通过实验发现，这些优化（尤其是使用寄存器和后变址寻址）带来了显著的性能提升，运行时间从约4.4秒缩短到了约2.9秒，后续的小优化也带来了持续的微小改进。
