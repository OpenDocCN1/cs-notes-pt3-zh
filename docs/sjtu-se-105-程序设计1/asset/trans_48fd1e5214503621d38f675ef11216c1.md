## ◆ 2 标识“循环变量”

## 5 循环体

- 在递归重新赋值中：
  - 先一次性计算所有新值
  - 然后赋值给变量
  - 这就是函数调用的语义
  - 但是，在C++语句中，每次只能计算一个

- 为了解决这个问题
  - 需要构建这些赋值语句的依赖图（dependency graph）
  - 这个图可以说明新值与旧值之间的依赖

## 5 循环体

- 构建依赖图：
  - 每个变量表示为一个顶点
  - 如果在计算变量 foo 的新值时读取了 bar 的值，则
    - 画一条从 foo 到 bar 的有向边
    - 不要画顶点到自身的边，例如 i = i + 1

## 5 循环体

- 构建依赖图:
  - 在阶乘例子中:
    - 在计算 n 的新值时，只读取了 n 自身的值
    - 而在计算 result 的新值时，读取了 result 自身和 n 的值
  - 我们忽略自引用，因此依赖图为:
    - n ← result

## 5 循环体

- 依赖图处理:
  - 如果对于一个变量，没有任何边以它为终点
    - 可以编码对其赋值，
    - 并删除它以及以它为起点的边

    - result 被删除，与result相关的边被删除
    - 依赖图变为：
      - n

## 5 循环体

- 依赖图处理：
  - 没有任何边以顶点n为起点，因此编写循环体第二行代码

```
int factorial(int num) {
    int n = num; result = 1;
    while (n!=0) {
        result *= n;
        n--;
    }
    return result;
}
```

## 5 循环体

- 依赖图处理：
  - 现在依赖图为空，编程完成
  - 棘手情况：
    - 依赖图中有环
    - 例如：

```
foo_helper(int bar, int baz){
    ...
    foo_helper(baz-1, bar-1);
}
```

## ◆ 5 循环体

- 依赖图处理：
  - bar 和 baz 互相依赖：`bar ↔ baz`
  - 不能先更新其中任何一个
  - 解决办法：
    - 引入“影子”变量，在赋值之前保存“新”值

```
int bar_new = baz-1;
int baz_new = bar-1;
bar = bar_new;
baz = baz_new;
```

## 5 循环体

- 依赖图处理：
  - 通过引入“影子”变量可以解决问题
    - 将依赖图中的环打破
  - 但是，影子变量增加了程序的阅读难度
    - 应该尽量避免使用

- 循环是非常强大的构建程序解决方案的方法
- 尾递归：
  - 无需对递归调用返回的结果再执行挂起的操作
- 普通递归
  - 与尾递归情况不同
- 例如，下面的函数就是尾递归：
  `int f(int x) { return f(x-1); }`
- 但是下面的函数就不是：
  `int f(int x) { return f(x) - 1; }`

- 尾递归解决方案的本质：
  - 只需要“常量内存空间”
    - 无论要解决的问题多“大”，只需要固定数量的栈内存帧
- 对于迭代解决方案也是如此
- 实际上，两个版本的factorial()非常相似
- 这种相似性不是偶然的
- 对于任何尾递归函数，都可编写出等价的迭代版本
- 换句话说，尾递归“只是”迭代

## 总结

- 这种等价性对于普通递归程序来说并不成立
  - 特别是，有些递归程序不能用常量内存空间来解决，例如，树的遍历问题

- 应该尽量以尾递归方式编写递归程序
- 如果某个递归不是尾递归（就像第一个版本的 factorial）
  - 必须引入一个助手函数，将其改写成尾递归
