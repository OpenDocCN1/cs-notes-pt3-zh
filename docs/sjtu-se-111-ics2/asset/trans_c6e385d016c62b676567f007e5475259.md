

## 程序中的分支行为

为什么分支（尤其是向后分支）更可能被执行而不是不被执行？

## 处理分支停顿

- 方法 1：停顿直到分支方向明确
  - 简单
- 方法 2：预测分支 **未被执行**
  - 按顺序执行后续指令
    - 在深流水线中比 Taken 更高效
  - PC+4 已计算好
  - 平均 **33%** 的分支未被执行

## 处理分支停顿

- 方法 3：预测分支 **被执行**
  - 平均 **67%** 的分支被执行
  - 但在深流水线中目标地址尚未计算
    - 仍会产生 1 个周期的延迟
  - 在分支目标在结果之前已知的机器上是有意义的（例如 Y86）

## 处理分支停顿

- 方法 4：**延迟**分支
  - 定义分支在之后 *n* 条指令执行后才发生
  - **分支延迟槽**
    - 分支延迟槽中的指令无论分支是否被执行都会被执行
    - 在早期的 RISC 机器中大量使用（例如 MIPS）
    - 具有深流水线的机器需要额外的延迟槽来避免分支惩罚

## 避免分支停顿的重要性

- 对现代微处理器至关重要，其每周期发出并执行多条指令
  - 需要持续的指令流来保持硬件忙碌
  - 控制冒险导致的停顿占主导
- 到目前为止，我们研究的是减少分支惩罚的静态方案

## 静态与动态

- **静态**方案：同一方案适用于每条分支指令
  
- **动态**方案：为每条指令单独选择最合适的方案
  - 例如，分支到循环顶部 // **Taken**
    ```c
    if (x == 0) return; // Not Taken
    ```
  - 可以根据观察到的行为**学习**合适的方案

## 分支预测器

- 两个部分
  - 目标缓冲：映射 PC 到被执行的目标
  - 方向预测器：映射 PC 到被执行/未被执行
- “映射 PC”是什么意思？
  - 使用某些 PC 位作为索引进入数据项数组

## 映射 PC

- 如果数据数组有 N 个条目
  - 需要 log(N) 位来索引它
- 选择哪 log(N) 位？
  - 去掉最低的 2 位之后的最低 log(N) 位
  - 最低有效位变化最频繁

## 映射 PC

- 如果两个 PC 在该子集位上具有相同模式（**别名**）
  - 我们得到一个无意义的目标（ intended for another PC）
  - 没关系，这本来就是一个猜测，如果错误可以恢复

## 分支预测（历史）缓冲

- 小内存，由分支指令的低位索引
  - 存储 **单个位** 的信息：T 或 NT
  - 起始为 T，每当分支行为与预测相反时翻转
  - 由 **取指** 阶段维护
  - 正确预测意味着 **无分支惩罚**

## 分支预测（历史）缓冲

- 该简单方案的问题
  - 对“大多数情况下被执行的分支”预测效果不佳
    - `e.g., for (i=0; i<10; i++) { ... }`
    - 循环重复执行会导致 **2 次误预测**
      - 最后一次迭代将 T 翻转为 NT
      - 第一次迭代将 NT 翻转为 T
    - 预测准确率为 **80%**

## 相关分支预测器

```
if (aa == 2)
    aa = 0;
if (bb == 2)
    bb = 0;
if (aa != bb)
    { ... }

DSUBUI R3, R1, #2
BNEZ  R3, L1      ; branch b1
DADD  R1, R0, R0
L1: DSUBUI R3, R2, #2
BNEZ  R3, L2      ; branch b2
DADD  R2, R0, R0
L2: DSUBU  R3, R1, R2
BEQZ  R3, L3      ; branch b3
```

- b3 的行为与 b1 和 b2 相关
  - 如果 b1 和 b2 均为 NT，b3 将为 T
