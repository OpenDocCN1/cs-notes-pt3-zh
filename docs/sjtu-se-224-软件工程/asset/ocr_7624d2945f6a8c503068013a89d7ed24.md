+   - 例如，4S系统的可移植性测试时，
+   - 在支持的MS Window和Linux两种操作系统场景的稳定版本上，可以方便地进行4S系统的安装。
+   - 用IE、Firefox等多个版本的浏览器都能正常访问。
+   - 能和已安装的MS Office等软件共存。
+   - 同时检查4S系统提供的安装文档和初始化数据。

# 可维护性测试

+   - 可维护性测试（maintainability testing）用以测试软件可被修改的能力，包括纠正、修改或软件对环境、需求变化的适应。
+   - 易分析测试，测试软件诊断缺陷或失效原因或识别修改所需分析的能力。
+   - 易修改测试，测试软件使指定的修改可以实现的能力。
+   - 易复查测试，测试软件避免由于软件修改而造成非预期结果的能力。
+   - 易测试测试，测试软件已修改性能被验证的能力。
+   - 维护性迁移测试，测试软件适应可靠性和相关的约束、标准或规定的能力。

+   - 一般，软件可维护性更多的是通过度量来进行评估。
+   - 常用可维护性度量，软件的复杂性、规模、可重用性、耦合度与内聚度、注释代码率、缺陷的平均修复成本、变更的平均实现成本等。
+   - 软件越复杂、规模越大、可重用性越低、耦合度越高、内聚度越小、注释代码率有数据占比越小、缺陷的平均修复成本和变更的平均实现成本越高，则软件可维护性越差。

# 其他测试策略

+   - 验收测试
+   - α测试和β测试
+   - 安装测试
+   - 回归测试

# 验收测试

+   - 针对应交付软件
+   - 验收测试（acceptance testing），是确定一个开发完成的软件系统是否符合其被批准、使用者/客户或其他授权实体所确定是否其接受该系统的正式测试。
+   - 验收测试是由用户为主的测试。验收测试原则上在用户所处环境进行，但经常用户同意也可以在开发机构内部根据用户环境下进行。
+   - 项目经理负责组织项目最终验收测试。验收组应由用户代表、相关专家、项目组成员等组成。验收根据合同、《需求规格》或《验收测试计划》对软件作成品进行验收测试。

# α测试和β测试

+   - 针对通用产品
+   - α测试是邀请小规模的、有代表性的潜在用户，在开发环境中，由开发人员“指导”下进行的测试（试用），并发现和记录使用过程中出现的各种软件缺陷，因此α测试是在一个受控的环境中进行的。
+   - β测试是由用户在一个或多个用户环境下进行的测试，产品正式发布前的系统测试形式。一组有代表性的用户和消费者作为在常规条件下使用该软件的测试员，由用户记录测试中发现的问题或任何期望改进的建议，报告给开发。
+   - β测试与α测试不同的是，β测试时开发通常不在测试现场，由用户去使用，软件在一个开发不能控制的环境中的“活的”试用。
