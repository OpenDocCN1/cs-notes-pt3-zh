

## 我们的期望

重启并运行恢复代码之后

- 1. 文件系统内部不变量得到维护
  例如，没有块同时位于空闲列表和文件中

- 2. 除最后少量操作外，其余操作均保存在磁盘上
  例如，我昨天写入的数据得以保留
  用户可能需要检查最后几个操作

- 3. 无顺序异常
  `$ echo 99 > result ; echo done > status`

## 我们的假设

简化假设：

- 磁盘是故障停止（fail-stop）磁盘，只执行文件系统发送给它的写入操作，不做其他任何事情
- 可能不会执行最后一次写入
- 因此：没有乱写，没有扇区衰减

## 为什么文件系统崩溃恢复很困难？

崩溃 = 停止/重启 CPU

让磁盘完成当前扇区的写入，假设没有硬件损坏，也没有对磁盘的乱写

目标：自动恢复

重启后，文件系统能否始终理解磁盘上的元数据？

考虑到崩溃可能发生在任意时刻？

示例

在 mkdir 期间崩溃，导致目录缺少 . 和 ..

在释放块期间崩溃

## 文件系统操作属性的术语

应用在重启和恢复后会看到什么效果？
creat("a"); fd = creat("b"); write(fd,...); crash

持久性（Durable）：操作的效果可见
a 和 b 都可见

原子性（Atomic）：操作的所有步骤要么全部可见，要么全部不可见
要么 a 和 b 都可见，要么都不可见

有序性（Ordered）：恰好可见操作的某个前缀
如果 b 可见，那么 a 也可见

## 恢复方法

- 1. 同步元数据更新 + fsck
  用于 xv6-rev0
  在检查期间，同步元数据，例如文件大小
- 2. 软更新（Soft update）（在 FFS 上修改的 FreeBSD 文件系统）
  软更新，本课程不涉及
- 3. 日志（ext 3/4）、xv6-rev6 及后续版本
  在执行实际的元数据更新之前，先记录该事件
  崩溃后，从日志中恢复

## 典型的权衡集合

文件系统确保能够恢复其元数据（真实文件系统的最低要求）

- 内部一致性
- 无悬空引用
- inode 和块空闲列表只包含未使用的项
- 同一目录中名称唯一，等等

## 弱语义文件系统提供的有限保证

- 对 creat、rename、delete 的原子性
- 通常不提供任何持久性
  - （creat("a")，然后崩溃，a 不存在）
- 通常不提供顺序保证

## fsck 做什么？

- 1. 检查超级块
  - 例如，确保文件系统大小大于已分配的块数
  - 如果有错误，使用超级块的备用副本
- 2. 检查空闲块
  - 扫描 inode、间接块、双重间接块等
  - 利用这些信息生成正确的分配位图版本
  - inode 位图也同样处理

## fsck 做什么？

- 3. 检查 inode 状态
  - 检查类型：普通文件、目录、符号链接等
  - 清除可疑的 inode 并清除 inode 位图
- 4. 检查 inode 链接
  - 通过扫描整个文件系统树来检查链接计数
  - 如果计数不匹配，修复该 inode
  - 如果 inode 已分配但没有任何目录包含它，则放入 lost+found
- 5. 检查重复项
  - 两个 inode 引用同一个块
  - 如果其中一个 inode 明显损坏，则清除它；否则，复制该块并各给一份副本

## fsck 做什么？

- 6. 检查坏块
  - 例如，指向某个越界地址
  - fsck 应该怎么做？只需移除该指针
- 7. 检查目录
  - 目录是 fsck 了解其更多语义的唯一文件类型
  - 确保 “.” 和 “..” 是前两个条目
  - 确保没有目录被链接多次
  - 同一目录中不能有相同的文件名
