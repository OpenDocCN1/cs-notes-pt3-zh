

## 重新调度软中断
- 软中断例程可以重新调度自身
- 这可能会导致用户级进程饥饿
- 软中断调度程序一次只运行有限数量的请求
- 其余的由内核线程 `ksoftirqd` 执行，该线程与用户进程竞争 CPU 时间

## Tasklets
- 基于软中断构建
- 可以动态创建和销毁
- 在调度它的 CPU 上运行（缓存亲和性）
- 执行期间单个 tasklet 被锁定；关于可重入性没有问题，代码无需加锁
- Tasklets 可以在多个 CPU 上并行运行
  - *相同* 的 tasklet 只能在一个 CPU 上运行
- 曾经是大多数延迟活动首选的机制，现在正在改变

## Tasklets 的问题
- 难以正确实现
- 必须小心不要睡眠
- 它们的优先级高于系统中的其他任务
- 如果编码不当，会产生不可控的延迟
- 正在讨论是否消除 tasklets
- 很可能会随着时间的推移慢慢淡出

## 工作队列
- 总是由内核线程运行
  - 由调度程序调度
- 软中断和 tasklets 在中断上下文中运行；工作队列具有伪进程上下文
  - 即，有内核上下文但没有用户上下文
- 因为它们具有伪进程上下文，所以可以睡眠
  - 工作队列由多个设备共享
  - 因此，睡眠会延迟队列上的其他工作
- 然而，它们仅限于内核；与之没有关联的用户模式
  - 不要尝试复制数据到/从用户空间

## 内核线程
- 总是在内核模式下运行
  - 同样，没有用户上下文
- 2.6.30 引入了 *线程化中断处理程序* 的概念
  - 从实时树引入
  - `request_threaded_irq()`
  - 现在每个下半部都有自己的上下文，不像工作队列
  - 想法是最终取代 tasklets 和工作队列

## 回顾
- 中断概念
  - IDT, Trap Num, 中断向量, IRQ, 系统调用号, …
  - 向量通常为 IRQ# + 32
  - 三重故障
- 中断过程
  - 设备, PIC (8259A), IDT, trap()
  - CPU 每个周期检查中断，如果中断已启用
  - 被屏蔽中断, 不可屏蔽中断

## Intel 保留的 ID 号
- 在 256 个可能的中断 ID 号中，Intel 将前 32 个保留为“异常”
- Linux 等操作系统可以自由使用剩余的 224 个可用中断 ID 号用于自己的目的（例如，来自外部设备的服务请求，或系统调用等其他用途）
- 示例：
  - 0: 除法溢出故障
  - 6: 未定义操作码
  - 7: 协处理器不可用
  - 11: 段不存在故障
  - 12: 栈故障
  - 13: 通用保护异常
  - 14: 页故障异常

## 总结：中断 vs 异常
- 术语各有不同，但对于 Intel：
  - **中断**（异步，设备生成）
    - 可屏蔽：设备生成，与 IRQs（中断请求线）相关联；可暂时禁用（仍处于挂起状态）
    - 不可屏蔽：某些关键硬件故障
  - **异常**（同步，来自软件）
    - 处理器检测到
      - 故障 – 可纠正（可重启）；例如页故障
      - 陷阱 – 无需重新执行；例如断点
      - 中止 – 严重错误；进程通常被终止（由信号）
    - 编程异常（**软件中断**）
      - int（系统调用），int3（断点）
      - into（溢出），bounds（地址检查）
