

## 中断处理哲学

- 在中断处理程序中尽量少做事情
- 将非关键操作推迟到稍后处理
- 结构：上半部和下半部
  - 上半部：做最少的工作并返回（ISR）
  - 下半部：延迟处理（软中断、tasklet、工作队列、内核线程）

## 警告：没有进程上下文

- 中断（与异常不同）不关联特定的指令
- 它们也不关联特定的进程（用户程序）
- 中断发生时正在运行的进程与该中断没有任何关系
- 中断处理程序不能休眠！

## 在中断处理程序中不能做什么？

- 不能休眠
  - 或调用可能休眠的函数
- 不能引用 `current`
- 不能用 `GPF_KERNEL` 分配内存（可能休眠），必须使用 `GPF_ATOMIC`（可能失败）
- 不能调用 `schedule()`
- 不能进行 `down()` 信号量调用
  - 但是，可以*进行* `up()`
- 不能与用户空间传输数据
  - 例如 `copy_to_user()`、`copy_from_user()`

## 中断栈

- 当中断发生时，使用哪个栈？
  - 异常：使用当前进程的*内核栈*，无论它是什么（总有一个进程在运行——如果没有别的，就是“空闲”进程）
  - 中断：硬 IRQ 栈（每个处理器一个）
  - 软中断：软 IRQ 栈（每个处理器一个）
- 这些栈由内核在启动时在 IDT 和 TSS 中配置

## 软中断

- **静态**分配：在内核编译时指定
- 数量有限：

| 优先级 | 类型 |
|---|---|
| 0 | 高优先级 tasklet |
| 1 | 定时器中断 |
| 2 | 网络传输 |
| 3 | 网络接收 |
| 4 | 块设备 |
| 5 | 普通 tasklet |

## 软中断何时运行？

- 由内核在多个时间点运行：
  - 系统调用之后
  - 异常之后
  - 中断之后（上半部/IRQ，包括定时器中断）
  - 当调度器运行 ksoftirqd 时
- 软中断例程可以在多个 CPU 上同时执行：
  - 代码必须是可重入的
  - 代码必须按需自行加锁
- 软中断运行时硬件中断始终启用

## 重新调度软中断

- 软中断例程可以重新调度自身
- 这可能会饿死用户级进程
- 软中断调度器一次只运行有限数量的请求
- 其余的由内核线程 `ksoftirqd` 执行，它会与用户进程竞争 CPU 时间

## Tasklet 的麻烦

- 难以正确使用
- 必须小心休眠问题
- 它们以高于系统中其他任务的优先级运行
- 如果编码不当，可能会产生不可控的延迟
- 关于消除 tasklet 的讨论持续进行中
- 可能会随着时间慢慢消失

## 工作队列

- 始终由内核线程运行
  - 由调度器调度
- 软中断和 tasklet 在中断上下文中运行；工作队列具有伪进程上下文
  - 即，有内核上下文但没有用户上下文
- 因为它们具有伪进程上下文，所以它们可以休眠
  - 工作队列由多个设备共享
  - 因此，休眠会延迟队列上的其他工作
- 然而，它们是内核专用的；没有与之关联的用户模式
  - 不要尝试将数据复制进/出用户空间
