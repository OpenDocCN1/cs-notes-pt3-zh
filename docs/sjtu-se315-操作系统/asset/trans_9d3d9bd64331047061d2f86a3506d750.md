## 总结：中断 vs 异常

- 术语各有不同，但对于 Intel 来说：
  - **中断**（异步，由设备产生）
    - 可屏蔽：由设备产生，与 IRQ（中断请求线）相关联；可暂时禁用（仍处于挂起状态）
    - 不可屏蔽：某些关键硬件故障
  - **异常**（同步，来自软件）
    - 处理器检测到
      - 故障 – 可纠正（可重启）；例如页故障
      - 陷阱 – 无需重新执行；例如断点
      - 中止 – 严重错误；进程通常被终止（由信号）
    - 编程异常（**软件中断**）
      - int（系统调用），int3（断点）
      - into（溢出），bounds（地址检查）

## 中断处理哲学

- 在中断处理程序中尽可能少做
- 将非关键操作推迟到以后
- 结构：上半部分和下半部分
  - 上半部分：做最少的工作并返回（ISR）
  - 下半部分：延迟处理（softirqs，tasklets，workqueues，kernel threads）

![](img/53ee1e3b0eba43505c7d530851f32f6f_437_0.png)

## 上半部分：现在就做！

- 技术上*就是*中断处理程序
- 执行最小的通用功能：保存寄存器，取消屏蔽*其他*中断。最终会撤销这些操作：恢复寄存器，返回到先前的上下文。
  - 通常用汇编语言编写
- IRQ 通常在上半部分持续时间内被屏蔽
- 最重要的一点：调用设备驱动程序中提供的正确中断处理程序（C 程序）
- 不想在这里做太多
  - IRQs 在一段时间内被屏蔽
  - 不希望栈变得太大
- 通常将请求排队并设置标志以便在下半部分中延迟处理

## 上半部分：找到处理程序

- 在现代硬件上，多个 I/O 设备可以共享单个 IRQ 以及中断向量
- 第一个区分因素是中断*向量*
- 多个*中断服务程序*（ISR）可以与一个向量相关联
- 调用与该 IRQ 相关的每个设备的 ISR
- 设备确定 IRQ 是否针对它

## 下半部分：稍后再做！

- 将工作推迟到以后的机制：
  - *softirqs*
  - *tasklets*（构建在 softirqs 之上）
  - *work queues*
  - *kernel threads*
- 所有都可以被中断

![](img/53ee1e3b0eba43505c7d530851f32f6f_440_0.png)

## 警告：无进程上下文

- 中断（与异常相反）与特定指令无关
- 它们也不与给定进程（用户程序）相关联
- 中断发生时正在运行的进程，与该中断没有任何关系
- 中断处理程序不能睡眠！

## 中断栈

- 当中断发生时，使用什么栈？
  - 异常：使用当前进程的*kernel stack*，无论它是什么（总是有某个进程在运行——如果没有其他进程，则是“空闲”进程）
  - 中断：硬 IRQ 栈（每个处理器一个）
  - SoftIRQs：软 IRQ 栈（每个处理器一个）
- 这些栈在启动时由内核在 IDT 和 TSS 中配置

## Softirqs

- **静态**分配：在内核编译时指定
- 数量有限：

| Priority | Type |
|---:|---|
| 0 | 高优先级 tasklets |
| 1 | 定时器中断 |
| 2 | 网络传输 |
| 3 | 网络接收 |
| 4 | 块设备 |
| 5 | 普通 tasklets |

## Softirqs 何时运行？

- 内核在以下各点运行：
  - 系统调用之后
  - 异常之后
  - 中断之后（上半部分/IRQs，包括定时器中断）
  - 当调度程序运行 ksoftirqd 时
- Softirq 例程可以在多个 CPU 上同时执行：
  - 代码必须是可重入的
  - 代码必须根据需要自行加锁
- 当 softirqs 运行时，硬件中断始终启用
