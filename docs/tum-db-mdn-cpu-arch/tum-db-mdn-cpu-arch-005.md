## 存储大型记录

![](img/6266b927f17879f9b10354c5965957d6_10.png)

![](img/6266b927f17879f9b10354c5965957d6_12.png)

上一节我们介绍了记录在数据库页中的标准存储布局。本节中，我们来看看当记录大小超过单个数据库页时，系统应如何处理。

![](img/6266b927f17879f9b10354c5965957d6_14.png)

数据库系统通常使用固定大小的页（例如16KB或32KB）来简化缓冲管理和恢复。这意味着每个元组必须能放入单个页中。然而，用户有时需要存储非常大的数据，例如文档或图片。

SQL通过两种数据类型显式支持大型对象：
*   **BLOB**：二进制大对象，用于存储原始字节序列。
*   **CLOB**：字符大对象，用于存储非常长的字符串。

![](img/6266b927f17879f9b10354c5965957d6_16.png)

一个典型的使用场景是在用户表中存储照片：
```sql
CREATE TABLE user (
    name VARCHAR(60),
    ...
    photo BLOB
);
```
这里的`photo`属性可能远大于一个页的大小。

### 处理大型对象的策略

系统不能简单地将大型属性跨页链式存储，因为这会导致读取不可预测数量的页，给缓冲和锁定带来噩梦。相反，标准做法是将大型对象与主元组分离开存储。

以下是实现分离存储的步骤：
1.  在主元组中，大型对象属性不存储实际数据，而是存储一个指向实际数据的标识符（如表ID或指针）。
2.  查询处理时，仅传递这个标识符。
3.  只有在最终需要将数据返回给用户时，才通过标识符检索实际的大型对象内容。

这种设计将大型对象的复杂性隔离在专门的存储模块中，保持了主元组的小巧。

![](img/6266b927f17879f9b10354c5965957d6_18.png)

### 存储大型对象本身

大型对象本身也需要映射到数据库页上。有两种主要方法：

![](img/6266b927f17879f9b10354c5965957d6_20.png)

![](img/6266b927f17879f9b10354c5965957d6_22.png)

**1. 使用B树风格存储**
这是一种非常优雅的方法。将大型对象数据分割成能放入单个页的块，存储为B树的叶子节点。内部节点则索引这些数据块的偏移量。

关键优化是使用**相对偏移量**而非绝对偏移量进行索引。例如，一个内部节点条目不写“100000-150000”，而是写“50000”，表示“从父分隔符开始的下50000字节”。这样，当在对象中间插入或删除数据时，只需要更新受影响的节点及其祖先节点（对数级），而无需更新右侧所有节点的绝对偏移量，大大提升了修改效率。

**2. 使用区段列表**
这是一种更简单的替代方案。在大型对象的描述符中，存储一个列表，列出组成该对象的所有数据页的起始位置和长度。为了控制列表大小，可以尝试一次性分配连续的多个页（一个区段）。

区段列表不如B树结构强大（例如难以在对象中间修改），但如果上层接口（如SQL）只支持整体读写大型对象，那么这种简单方案可能就足够了。

### 优化短大型对象

在实践中，许多声明为`BLOB`或`CLOB`的字段（如`VARCHAR(200)`的替代品）实际上存储的是短字符串。系统应该优化这种常见情况。

一个智能的系统（如PostgreSQL的`TEXT`类型及其TOAST机制）会采用分层策略：
1.  **内联存储**：如果字符串非常短（例如小于8字节），直接将其编码并存储在元组的指针ID位置。
2.  **单独页存储**：如果字符串较长但仍能放入一个页，则分配一个单独的页来存储，元组中只存储指向该页的指针。
3.  **完整大型对象机制**：只有真正巨大的数据才会使用B树或区段列表等完整机制。

![](img/6266b927f17879f9b10354c5965957d6_24.png)

这种优化确保了在绝大多数情况下都能获得高性能。

## 索引结构简介

![](img/6266b927f17879f9b10354c5965957d6_26.png)

![](img/6266b927f17879f9b10354c5965957d6_28.png)

![](img/6266b927f17879f9b10354c5965957d6_30.png)

![](img/6266b927f17879f9b10354c5965957d6_31.png)

到目前为止，我们只能通过**全表扫描**来查找数据，即线性读取关系中的所有页和元组。这对于选择性查询或主键约束检查来说效率极低（时间复杂度为O(n²)）。

![](img/6266b927f17879f9b10354c5965957d6_33.png)

索引结构用于支持两种主要查询类型：
*   **点查询**：查找具有特定属性值的元组（例如 `WHERE id = 7`）。
*   **范围查询**：查找属性值在某个范围内的元组（例如 `WHERE x BETWEEN 10 AND 20`）。

目标是实现次线性时间复杂度的查找。

![](img/6266b927f17879f9b10354c5965957d6_35.png)

## B树与B+树

### 为什么选择B树？

![](img/6266b927f17879f9b10354c5965957d6_37.png)

B树（及其变体）是外部存储中最主流的多路搜索树数据结构，原因如下：
*   **很浅的树高**：节点度数大（K值大），使得即使存储数十亿条目，树高也通常只有3-4层。查找复杂度为 O(logₖ N)。
*   **对比红黑树**：红黑树虽然也是O(log N)，但基数小（2），树高可能达到20-40层。在磁盘上，每层都可能需要一次I/O，性能差距巨大。B树在内存中通常也更快。
*   **易于实现**：B树（尤其是B+树）的平衡和维护算法比红黑树等内存数据结构更直观，更容易正确实现。

### B+树优于B树

![](img/6266b927f17879f9b10354c5965957d6_39.png)

现代数据库几乎都使用B+树，而非经典B树。两者核心区别在于数据存储位置：
*   **经典B树**：键值对存储在**所有节点**（内部节点和叶子节点）中。
*   **B+树**：键值对**仅存储在叶子节点**。内部节点仅存储用于路由的**分隔键**，不存储实际数据指针。

![](img/6266b927f17879f9b10354c5965957d6_41.png)

B+树的优势：
1.  **更高的扇出**：内部节点条目更小（只有键，没有数据指针），因此单个页能容纳更多条目。更高的扇出意味着更浅的树和更快的查找。
2.  **更简单的维护操作**：插入和删除时，绝大多数操作只影响叶子节点。分隔键不必是实际存在的键值，这减少了内部节点更新的频率，简化了算法。

![](img/6266b927f17879f9b10354c5965957d6_43.png)

### B+树的物理布局

![](img/6266b927f17879f9b10354c5965957d6_45.png)

![](img/6266b927f17879f9b10354c5965957d6_46.png)

**内部节点页**的布局通常如下：
```
[日志序列号 LSN][上层指针][条目数量 N][(子页指针 P1, 键 K1), (P2, K2), ..., (PN, KN)]
```
*   **上层指针**：指向大于本节点所有键的子树。
*   条目按键排序，支持快速查找。

![](img/6266b927f17879f9b10354c5965957d6_48.png)

![](img/6266b927f17879f9b10354c5965957d6_49.png)

![](img/6266b927f17879f9b10354c5965957d6_51.png)

**叶子节点页**的布局通常如下：
```
[日志序列号 LSN][标记值（如-1）][条目数量 N][(键 K1, 元组ID T1), (K2, T2), ..., (KN, TN)][下一个叶子节点指针]
```
*   **标记值**：用于在遍历时区分内部节点和叶子节点（例如，检查特定字段是否为-1）。
*   **下一个叶子节点指针**：将所有叶子节点串联成一个有序链表。这对于高效执行范围查询至关重要：只需找到范围的起始点，然后沿链表扫描即可。

![](img/6266b927f17879f9b10354c5965957d6_53.png)

![](img/6266b927f17879f9b10354c5965957d6_55.png)

### B+树查找算法

![](img/6266b927f17879f9b10354c5965957d6_57.png)

![](img/6266b927f17879f9b10354c5965957d6_59.png)

![](img/6266b927f17879f9b10354c5965957d6_61.png)

查找从根节点开始，递归向下：
1.  设当前节点为`C`。
2.  如果`C`是叶子节点，在`C`中搜索键`K`，返回结果。
3.  如果`C`是内部节点，在`C`中查找**第一个大于等于`K`的键**。
    *   如果找到，跟随其对应的子指针。
    *   如果未找到（`K`大于所有键），跟随上层指针。
4.  将子节点设为新的`C`，重复步骤2。

![](img/6266b927f17879f9b10354c5965957d6_63.png)

![](img/6266b927f17879f9b10354c5965957d6_65.png)

**关键点**：在节点内部查找时，因为条目数量可能很多（成千上万），必须使用高效的搜索算法，而不是线性扫描。

## 优化节点内查找

![](img/6266b927f17879f9b10354c5965957d6_67.png)

![](img/6266b927f17879f9b10354c5965957d6_69.png)

在B+树节点（页）内部查找键时，性能至关重要。我们有两种优化手段：

![](img/6266b927f17879f9b10354c5965957d6_71.png)

![](img/6266b927f17879f9b10354c5965957d6_73.png)

### 1. 无分支二分查找

![](img/6266b927f17879f9b10354c5965957d6_75.png)

![](img/6266b927f17879f9b10354c5965957d6_77.png)

![](img/6266b927f17879f9b10354c5965957d6_79.png)

标准的二分查找循环中包含`if`条件判断，这可能导致CPU分支预测失败，降低性能。

![](img/6266b927f17879f9b10354c5965957d6_81.png)

![](img/6266b927f17879f9b10354c5965957d6_83.png)

![](img/6266b927f17879f9b10354c5965957d6_85.png)

我们可以重写算法，利用条件计算来消除循环内的分支。基本思想是将`if`判断转换为基于比较结果的算术运算，从而避免CPU流水线停顿。对于页内搜索（数据量在几百到几千），这种无分支二分查找通常更快。

![](img/6266b927f17879f9b10354c5965957d6_87.png)

![](img/6266b927f17879f9b10354c5965957d6_89.png)

### 2. 插值搜索（针对数值型键）

![](img/6266b927f17879f9b10354c5965957d6_91.png)

![](img/6266b927f17879f9b10354c5965957d6_92.png)

![](img/6266b927f17879f9b10354c5965957d6_94.png)

如果键是数值类型（如整数），并且我们在遍历树时已经知道了当前搜索键的上下界（来自父节点的分隔键），我们可以做得比二分查找更好。

**插值搜索**原理：
1.  **估算位置**：根据搜索键`K`、已知下界`L`和上界`U`，按比例估算`K`在当前节点中的大概位置：`pos ≈ ((K - L) / (U - L)) * 节点条目数`。
2.  **指数拓展**：从估算位置开始检查。如果猜小了，则以指数级增长的步长向右跳（1, 2, 4, 8...）；如果猜大了，则向左跳。直到确定包含目标键的小范围。
3.  **局部二分查找**：在这个小范围内进行精确的二分查找。

如果数据分布相对均匀，插值搜索可以极大地减少比较次数，直接跳到目标附近。即使估算不准，后续的指数拓展和局部二分查找也能保证效率不会比纯二分查找差很多。

## 总结

![](img/6266b927f17879f9b10354c5965957d6_96.png)

本节课我们一起学习了数据库系统中处理大型数据对象的方法和B树索引的核心原理。

![](img/6266b927f17879f9b10354c5965957d6_98.png)

我们首先探讨了当元组超过单页大小时，如何通过分离存储（使用B树或区段列表管理大型对象本身，在主元组中只存指针）来保持核心数据结构的紧凑和高效。同时，系统应优化短大型对象的存储，将其内联或单独存页。

接着，我们引入了索引的必要性，并深入讲解了B+树这一最重要的索引结构。我们对比了B+树与经典B树、红黑树的优劣，详细描述了B+树的物理布局、查找算法，并特别强调了通过**无分支二分查找**和**插值搜索**来优化节点内查找性能的重要性。
