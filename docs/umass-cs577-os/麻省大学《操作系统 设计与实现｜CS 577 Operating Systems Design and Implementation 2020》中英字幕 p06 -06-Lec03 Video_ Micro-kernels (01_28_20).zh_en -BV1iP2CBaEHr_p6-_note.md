# 操作系统设计与实现：03：微内核 (01/28/20)

在本节课中，我们将学习微内核架构的设计理念。我们将从Unix的历史讲起，探讨为何微内核设计有其价值，并重点分析设备驱动程序对操作系统稳定性的影响。最后，我们将介绍Minix微内核的基本结构。

## Unix与Minix的历史回顾

上一节我们介绍了操作系统的基本硬件支持。本节中，我们来看看操作系统设计思想的发展历程。

Unix操作系统的历史始于20世纪60年代。当时，麻省理工学院、贝尔实验室和通用电气公司合作开发了一个名为Multics的大型分时系统项目。Multics项目过于复杂，最终在商业上失败了。然而，它启发了后续的工作。

贝尔实验室的研究人员肯·汤普森等人利用一台闲置的PDP-7计算机，开发了一个简化版的操作系统，最初命名为UNICS，后来演变为Unix。为了提升可移植性，他们使用C语言重写了Unix，并将其源代码授权给大学用于教学和研究。

到了20世纪80年代，安德鲁·塔能鲍姆教授为了教学目的，开发了一个小型、开源的Unix克隆系统，命名为Minix。Minix的设计目标是简洁、易于理解，并采用了微内核架构。Minix的早期版本在调试时曾遇到一个有趣的硬件问题：8088处理器过热时会触发一个未公开的中断，导致系统崩溃。修复这个问题后，Minix得以继续发展。

1991年，芬兰学生林纳斯·托瓦兹受到Minix的启发，开始开发自己的操作系统内核，这就是后来的Linux。Linux最初借鉴了Minix的部分代码，但最终发展成为一个庞大、功能丰富的宏内核系统。

关于微内核与宏内核的优劣，在90年代曾有一场著名的论战，即塔能鲍姆与托瓦兹之间的“Linux已过时”之争。这场辩论的核心在于操作系统的设计哲学。

## 为何要考虑微内核：设备驱动程序的视角

了解了历史背景后，我们来看看一个具体问题，它凸显了微内核设计的优势：设备驱动程序的可靠性。

现代操作系统崩溃的主要原因之一是设备驱动程序存在缺陷。在宏内核架构中，所有内核代码（包括驱动程序）运行在同一个特权地址空间。这意味着，驱动程序中的一个错误可能导致整个内核崩溃，进而使整个系统宕机。

以下是相关统计数据：
*   据估计，操作系统内核中约70%的代码是设备驱动程序。
*   设备驱动程序的缺陷率是内核其他部分的3到7倍。
*   在Windows XP时代，约80%的“蓝屏死机”故障是由驱动程序错误引起的。

驱动程序问题频发，部分原因是它们通常由第三方硬件厂商开发，其代码质量和测试标准可能与核心内核开发团队不同。将这些可能存在缺陷的代码直接放入高特权的内核空间，带来了巨大的稳定性风险。

## 提升可靠性的不同架构方案

面对驱动程序带来的可靠性挑战，业界提出了几种不同的软件架构方案。

### 方案一：宏内核与Nooks
Nooks是一个研究项目，旨在不改变宏内核整体架构的前提下提升其可靠性。其核心思想是在每个设备驱动程序周围包裹一个保护层（Nooks Wrapper）。这个保护层会检查驱动程序的所有内存访问和函数调用，防止其错误行为影响到内核的其他部分。虽然这能阻止大部分错误传播，但驱动程序本身仍运行在内核空间，无法完全隔离所有故障。

### 方案二：虚拟化
另一种思路是利用虚拟化技术。将原有的操作系统（包含驱动程序）运行在一个虚拟机中，而将设备驱动程序单独移出，运行在另一个轻量级虚拟机里。两个虚拟机通过通信机制协作。这样，驱动程序的崩溃只会影响它所在的虚拟机，而主操作系统虚拟机可以继续运行。这需要对操作系统进行一定的重构。

### 方案三：混合内核
混合内核是宏内核和微内核之间的折中方案。例如，早期的L4Linux项目将完整的Linux内核作为一个单独的“大”进程运行在L4微内核之上。虽然一些核心服务被移出，但驱动程序仍留在Linux进程中，因此其崩溃仍会导致Linux服务中断，但不会使底层微内核崩溃。

### 方案四：纯微内核
纯微内核架构是解决问题的根本方法。在这种设计中，内核本身（微内核）非常小，仅提供最基础的服务，如进程间通信（IPC）、基本的地址空间管理和线程调度。所有其他服务，包括**所有的设备驱动程序**、文件系统、进程管理等，都作为独立的用户态进程（或称服务器）运行。

其优势可以用一个简单的模型表示：
```
系统可靠性 ∝ （驱动程序运行在用户态）
```
当驱动程序作为用户进程运行时，其内部的缺陷通常只会导致该进程崩溃，而不会波及微内核或其他系统服务进程。系统可以监视这些服务进程，并在其崩溃后重新启动它们，从而保持整体服务可用。

当然，这种架构的代价是性能。由于系统服务间需要通过IPC进行通信，而不是直接的内核函数调用，因此会引入额外的开销。这是微内核设计一直面临的主要挑战。

## 其他可靠系统设计思路：Singularity

在探讨微内核的同时，我们也看看另一种截然不同的设计思路：使用类型安全的编程语言从头构建操作系统。微软研究的Singularity项目就是代表。

![](img/962f0ef745b03181c4e016d695f735b6_3.png)

Singularity的核心思想是：许多软件缺陷源于C/C++这类语言本身的不安全性（如指针错误、内存泄漏、类型混淆）。因此，他们使用一种类型安全的语言（Singularity C#）重写整个操作系统。编译器在编译时就能进行严格的检查，阻止大量常见错误。

更激进的是，Singularity甚至移除了传统的内存地址空间隔离。所有操作系统组件和应用程序都运行在同一个地址空间中。依赖语言和编译器的安全保证来替代硬件的内存保护。这带来了极高的性能潜力，但也牺牲了动态加载代码（如浏览器插件）的灵活性，因为所有代码都必须经过严格的静态验证。

## Minix 3 微内核架构详解

现在，让我们聚焦到本课程将深入研究的Minix 3系统，它是一个典型的纯微内核设计。

Minix 3的架构可以清晰地映射到其源代码目录结构：
*   `kernel/`：微内核本身，代码量很小（约4000行）。
*   `servers/`：各种系统服务进程，如文件系统、进程管理器等。
*   `drivers/`：所有设备驱动程序，每个驱动都是一个独立的用户进程。
*   `lib/`：为用户程序和系统服务提供的库。

### 核心组件交互示例

在Minix中，系统功能的完成依赖于这些独立进程间的协作。以下通过两个例子说明：

**1. 创建新进程 (`fork`)**
当一个用户程序调用`fork()`创建新进程时：
1.  用户库将请求转化为一个IPC消息，发送给**进程管理器（PM）** 服务器进程。
2.  **进程管理器（PM）** 需要为新进程分配内存，于是它发送一个IPC消息给**内存管理器（MM）** 服务器进程。
3.  **内存管理器（MM）** 决定如何分配，但它不能直接操作硬件页表。因此，它通过一个特殊的系统调用，请求**微内核**中的系统任务（`SYSTASK`）执行实际的内存映射操作。
4.  操作完成后，结果通过IPC链逐级返回，最终新进程被创建。

**2. 读取文件 (`read`)**
当一个进程读取文件时：
1.  请求通过IPC发送给**文件系统（FS）** 服务器。
2.  **文件系统（FS）** 检查其缓存。若未命中，则需要从磁盘读取。
3.  **文件系统（FS）** 发送一个IPC请求给相应的**磁盘驱动程序**进程。
4.  **磁盘驱动程序**进程通过系统调用请求**微内核**执行实际的I/O操作（向磁盘控制器发送命令）。
5.  数据读回后，沿原路径通过IPC返回给最初发出请求的进程。

### 微内核的关键职责

Minix的微内核主要提供三大基础功能：

1.  **进程间通信（IPC）**：这是微内核的基石。它提供发送、接收、回复消息的原语。通信通常是同步和阻塞的。
    *   `send(dest, &message)`：发送消息到目标进程，并阻塞等待回复。
    *   `receive(source, &message)`：阻塞等待来自特定源进程的消息。
    *   `reply(dest, &message)`：向等待回复的进程发送答复。

2.  **精细的权限控制**：微内核知道每个进程的“权限级别”。例如，普通的用户进程不能直接向微内核发送某些特权请求，而必须通过像进程管理器这样的服务进程中转。微内核强制执行这些通信策略。

3.  **底层硬件抽象**：通过系统任务（`SYSTASK`）和时钟任务（`CLOCKTASK`）等内部组件，微内核处理最底层的特权操作，如修改页表、设置定时器、处理硬件中断等。设备驱动程序通过系统调用请求这些服务来完成其工作。
