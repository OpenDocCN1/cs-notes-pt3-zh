# 操作系统设计与实现：09：Linux 架构 (02/20/20)

在本节课中，我们将学习 Linux 操作系统的核心架构。我们将探讨其历史背景、设计哲学、进程管理以及调度机制，并与 Minix 系统进行对比，以理解其独特之处。

## 概述

Linux 起源于一个个人项目，旨在创建一个自由、开源的类 Unix 操作系统。它与 Minix 系统在许多概念上相互借鉴，但在设计决策和实现细节上存在显著差异。Linux 内核是一个庞大且复杂的单体内核，支持广泛的硬件平台，其设计强调可移植性和性能。

## Linux 的历史与设计哲学

上一节我们介绍了课程概述，本节中我们来看看 Linux 的起源和其核心设计理念。

Linux 的诞生源于 Linus Torvalds 因 Minix 的许可问题而无法获得其源码的挫折感。它并非第一个尝试重建 Unix 生态系统的项目，但最终成为了最成功的一个。早期采用者如 NASA 因其免费、类 Unix 且功能齐全而选择了它。

Linux 的系统模型与 Minix 不同。它是一个单体内核，所有核心功能（如驱动程序、文件系统、加密模块）都运行在内核空间。应用程序只能通过系统调用接口与内核通信。

**核心概念**：Linux 内核模型
```
用户空间应用程序 -> 系统调用接口 -> 内核子系统（进程管理、内存管理、文件系统、设备驱动等）
```

内核编程与用户空间编程有本质区别。在内核中：
*   没有内存保护机制，内核代码可以访问所有物理内存。
*   通常避免使用浮点运算。
*   每个进程有固定大小的内核栈。
*   必须谨慎处理并发与同步问题，因为中断可能在任何时候发生。

可移植性对 Linux 至关重要，这使其成为从嵌入式设备到云服务器的首选。然而，支持一切也导致了内核的急剧膨胀，目前已有超过 2500 万行代码，这带来了巨大的维护和安全挑战。

## 进程管理

了解了 Linux 的整体设计后，本节我们深入其进程管理机制。

在 Linux 中，进程是系统工作的基本单元。程序本身是静态的代码和数据，而进程是正在执行的程序的动态实例，包括代码、数据、打开的文件等。

Linux 内核使用一个名为 `task_struct` 的数据结构来描述进程（在 Linux 中，进程常被称为“任务”）。这个结构体非常庞大（约 500 行代码），包含了进程的所有信息，如进程ID（PID）、状态、优先级、内存映射、文件描述符等。一个 `task_struct` 实例的大小可达 1.7 KB。

所有进程的 `task_struct` 通过一个双向链表连接起来，形成任务列表（`task list`）。这使内核能够高效地遍历系统中的所有进程。工具如 `ps` 或 `top` 就是通过读取这个列表来工作的。

进程间存在父子关系。除了初始的 `init` 进程（PID 1），每个进程都有一个父进程。这种关系形成了进程树，并被记录在 `task_struct` 中。当父进程终止时，其子进程会被“过继”给 `init` 进程，成为“孤儿进程”。

进程创建遵循经典的 `fork()` 和 `exec()` 模型：
1.  `fork()`：创建当前进程的一个副本（子进程），两者最初几乎完全相同。
2.  `exec()`：将新的程序代码加载到子进程的地址空间中，并开始执行。

为了提高效率，Linux 使用了写时复制（Copy-On-Write， COW）技术。`fork()` 时并不立即复制父进程的数据，而是共享同一份物理内存页。只有当父或子进程试图修改某个内存页时，内核才会为该页创建一个独立的副本。

## 线程模型

进程内部可以包含多个执行流，即线程。接下来我们看看 Linux 如何实现线程。

Linux 对线程的实现有其独特之处。内核并没有为线程设计专门的数据结构，而是将线程视为共享某些资源（如地址空间、文件描述符表）的轻量级进程。每个线程都有自己的 `task_struct`，因此在内核调度器看来，线程和进程没有本质区别。

以下是几种线程映射模型：
*   **Minix 模型（M:1）**：多个用户线程映射到一个内核线程。
*   **Linux 模型（1:1）**：每个用户线程对应一个独立的内核线程。这是 Linux 的默认模型。
*   **M:N 模型**：M 个用户线程映射到 N 个内核线程。现代编程语言如 Go 的 Goroutine 采用此模型，以在并发性和并行性之间取得平衡。

在 Linux 中，线程是使用 `clone()` 系统调用创建的。`clone()` 接受一系列标志参数，允许调用者精细控制哪些资源（如内存空间、文件描述符表）在线程间共享。

**核心概念**：创建线程的 `clone()` 调用示例
```c
clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND, 0);
```
上述标志表示新线程与调用者共享内存空间、文件系统信息、文件描述符表和信号处理程序。

此外，内核自身也会创建内核线程来执行后台任务（如内存清理、磁盘缓存刷新）。这些线程没有对应的用户空间进程，完全运行在内核态。

## 进程终止与调度

进程有生亦有灭，并且需要被公平、高效地调度执行。本节将探讨这两个主题。

进程终止有两种主要方式：
1.  **正常退出**：进程主动调用 `exit()` 系统调用或从 `main()` 函数返回。
2.  **强制终止**：内核或其他进程向目标进程发送终止信号（如 `SIGKILL`）。

进程终止并非瞬间完成。当进程调用 `exit()` 后，它会进入“僵尸”（Zombie）状态。此时，进程已释放大部分资源，但其 `task_struct` 仍然保留，以便父进程通过 `wait()` 系列系统调用获取其终止状态信息。父进程执行 `wait()` 后，内核才会最终清理并释放僵尸进程的 `task_struct`。如果父进程先于子进程终止，子进程会成为孤儿进程，并由 `init` 进程接管并负责清理。

现在，我们转向进程调度。Linux 是一个支持抢占的多任务操作系统，这意味着内核可以在任何时刻中断正在运行的进程，并切换到另一个进程。

Linux 调度器的发展经历了多个阶段：
*   **O(n) 调度器（2.4版）**：简单但不可扩展，对交互式应用不友好。
*   **O(1) 调度器（2.6版早期）**：引入多队列，解决了扩展性问题，但交互性仍有不足。
*   **完全公平调度器（CFS，2.6.23版至今）**：当前默认调度器，旨在公平地分配CPU时间。

CFS 的核心思想是“完全公平”。它不再使用传统的时间片概念，而是为每个进程分配一个处理器使用比例（权重）。CFS 使用一个红黑树来组织可运行进程，树的键是进程的“虚拟运行时间”（`vruntime`，即经权重调整后的实际运行时间）。调度器总是选择 `vruntime` 最小的进程来运行，这保证了所有进程能按权重比例公平地推进。

CFS 区分交互式（I/O密集型）和批处理（CPU密集型）应用，通过动态调整权重来保证交互式应用的响应速度。

Linux 调度器的一个关键特性是**模块化**。内核中可以同时存在多个调度器类（如 CFS、实时调度器、截止时间调度器），每个类有不同的优先级。内核根据任务的调度策略将其分配给相应的调度器类，并优先运行高优先级类中的任务。

## 总结

本节课中我们一起学习了 Linux 操作系统的核心架构。我们从其历史起源和设计哲学讲起，理解了其单体内核模型与内核编程的特殊性。我们深入探讨了进程管理，包括 `task_struct` 数据结构、进程创建（`fork`/`exec`/COW）和终止机制。接着，我们分析了 Linux 独特的线程模型（1:1映射）以及如何使用 `clone()` 创建线程。最后，我们研究了进程调度，重点介绍了当前默认的完全公平调度器（CFS）的工作原理及其追求公平性的设计目标，并了解了 Linux 调度器模块化的特点。通过与 Minix 的对比，我们更清晰地看到了 Linux 在设计选择和实现上的不同路径。
