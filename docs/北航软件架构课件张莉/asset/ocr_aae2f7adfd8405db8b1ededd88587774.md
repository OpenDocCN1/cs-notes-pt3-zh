# 可用性的一般场景

刺激源：用户、系统或外部环境产生的刺激；刺激：刺激源发出的请求；环境：正常、可能慢；响应：速度、延迟、等待时间等；响应度量：响应时间、可用性、吞吐量等。

+   - 目标：应用场景的结果，将要执行的请求或需要。
+   - 示例：在正常操作期间，进程收到一个请求并对其进行响应。

# 可用性场景示例

刺激源：系统外部事件；刺激：未预料到的请求；环境：正常操作；响应：通知操作人员或采取措施；响应度量：在规定时间内完成响应。

> 刺激源很重要，因为不同的刺激源可能要求软件作出不同的响应。

> 环境也可以影响响应。例如：系统已经处于非故障状态，为零件降低方式不会不同时。

# 可修改性场景示例

可修改性场景示例：开发人员希望改变系统的行为，以便增加新的行为。这些变更可能造成代码、数据和环境的变化。

刺激源：开发人员；刺激：提出改变用户需求；环境：设计时；响应：修改产生影响的代码。

# 生成质量属性场景

+   - 可以把具体场景的集合视为系统的质量属性需求。
+     - 对于每个场景是足够具体的，因此对设计师是有意义的。
+     - 响应的细节具有足够的意义，可测试系统是否实现了该响应。
+   - 可采用表的方式描述

# 例如：可用性的一般场景生成

| 场景 | 可能的值 |
|---|---|
| 源 | 系统内外、系统外部 |
| 刺激 | 错误、故障、病毒、时间、响应 |
| 制品 | 系统的处理器、通信通道、持久存储器、进程 |
| 环境 | 正常操作、降级模式 |
| 响应 | 系统知道检测到事件，并进行如下一个或多个活动：记录处理、通过活动的各方、包括用户在内的其他系统、根据适当的规则处理；在一段时间范围内完成响应；系统的资源管理能力 |
| 响应度量 | 系统必须在可用的时间内响应；可用时间；系统可以在响应模式下运行的时间间隔 |


# 实践中的质量属性场景

+   - 一般场景提供了一个生成大量一般的、独立于系统的、特定于质量属性的场景的框架。如：
+     - 一般场景：一个要求改变功能的请求达到，必须在一个指定的时间内，在开发过程中的一个特定时间段改变功能。
+     - 特定于系统的场景：“一个要求在某天的系统中增加新浏览器支持的请求达到，必须在2周内进行该项改变。”
+   - 可见，一个一般场景可能含有多个特定于系统的场景。
