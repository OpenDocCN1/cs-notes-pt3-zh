

## View-1 中的信息

+   1. 主要呈现（图表、表格或大纲）
+      - 如果是图形的，始终包含一个键或引用以解释符号。
+   2. 元素目录
+      - 对主要呈现中的元素进行散文描述
+      - 包含超出该视图范围的外部元素
+      - 元素的软件接口（或通过引用纳入接口规范）
+      - 元素的行为。用例如序列图或状态图来记录此内容。

## View-2 中的信息

+   3. 其他信息
+      - 驱动架构需求
+      - 设计决策的理由（包括被拒绝的替代方案）
+      - 分析、原型和实验的结果，这些结果提供了架构适合用途的证据
+      - 内置于架构中的可变性机制——也许该架构是参考架构。可参数化的点（例如池中的实例数量）
+      - 元素可以被复制、省略或替换的地方
+      - 上下文图显示软件元素与外部实体的关系

## 超出 Views-1 的文档

+   1. 文档路线图
+      - 解释文档是如何组织的以帮助利益相关者完成工作
+      - 解释所选视图以及原因
+   2. 系统概述
+      - 对系统及其目的、功能、主要外部接口和主要质量属性的散文描述。
+      - 其目标是为新项目成员提供背景。
+      - 如果整体系统文档中存在概述，它可以指向其他地方的概述。

## 超出 Views-2 的文档

+   3. 架构上重要的需求
+      - 可能引用单独的需求文档
+      - 三种需求
+        - 功能需求（例如用例）
+        - 质量属性需求（例如场景）
+        - 设计约束；例如，“系统应使用 J2EE 开发。”
+   4. 系统概述
+      - 表格显示一个视图中的元素如何对应于另一个视图中的元素
+      - 模块映射到模块
+      - 模块映射到组件和连接器

## 超出 Views-3 的文档

+   5. 架构分析和理由
+      - 采用的主要架构方法
+      - 记录的设计决策（包括被拒绝的替代方案）
+      - 如果进行了架构评估，结果可以放在这里。
+   6. 将架构映射到需求
+      - 显示每个需求如何由架构的一个或多个元素或架构方法满足

## Module Summary-1

架构文档的主要用途包括构建、教育和分析。记录架构就是记录其视图，然后记录适用于多个视图的信息。视图是对结构的表示。有三种架构视图类型：

1. 模块视图
2. C&C 视图
3. 分配视图

## Module Summary-2

图表是不够的！图表中的元素必须得到解释。

视图本身是不够的！视图必须通过解释文档组织和整个系统来补充。
