

## 4.4.3 ORACLE Security Design

### Passwords and Resources

A profile is a named collection of password and resource limit settings. Oracle has a profile named DEFAULT. All items in the default profile are unrestricted; if no profile clause is specified when creating a user, the system assigns DEFAULT to that user.

Oracle allows the DBA to modify DEFAULT and user-defined profiles using the ALTER PROFILE command. It allows dropping DEFAULT and user-defined profiles using the DROP PROFILE CASCADE command.

When creating a user, you need to determine the username and authentication mechanism, specify the default tablespace and temporary tablespace, determine quotas on the relevant tablespaces, and specify the user's profile.

ORACLE application systems generally define a series of users and profiles, define a series of roles, and then grant (or assign) the roles and profiles to users.

### Privileges and Roles

Oracle has more than 100 system privileges, including system-wide operational privileges such as creating tablespaces, object management privileges within a user schema such as creating tables, and object management privileges within any schema such as creating any table. System privileges and object privileges can be granted to or revoked from users through GRANT or REVOKE statements.

A role is a named set of related privileges. Roles are system-wide; they belong neither to a particular user nor to a particular schema. System privileges and object privileges can be granted to a role, a role can be granted to another role, and ultimately the role is granted to users, thereby facilitating Oracle security management.

The steps for using roles are: create a role, grant the appropriate privileges to the role, and grant the role to specific users.

Some predefined roles are available in Oracle, such as DBA and SELECT_CATALOG_ROLE, and the DBA can use them directly.

### Users of the Application System

Security design for application systems generally classifies users, and then sets up, maintains, and manages them according to user type.

- Database Administrator (DBA): The default database administrators internal, sys, and system all have DBA privileges. Operations such as opening, closing, and recovering the database require using internal; use sys to modify important database parameters; use system for other general administration.
- Owner (OWNER): For large application systems, objects are often divided according to different user ownership, so different users own different database objects. The user who creates a database object is called the owner (schema) of the object. Such users need the RESOURCE privilege.
- General User (USER): General users are the end users of the application system. Such users only need the CONNECT privilege for the database, but their role privileges and object usage privileges need to be further planned and designed based on specific work and applications.

### General Users of the Application System

Besides creating a series of database objects, application systems also create a series of application programs, with different programs performing different operations. For general users, using the database system begins with using user-managed application programs, and their rights to use certain applications are often restricted. In this situation, the approach is to establish a user-managed application program layer between the database and the application programs, granting each user the appropriate database privileges and application usage rights.

Configuration for general users: system-level privileges are limited to the CONNECT role, object-level privileges are limited to custom roles of the relevant application system, and application usage privileges are limited to the usage level of the relevant applications.

Multiple levels of checking and verification are performed within the application system:

- 1) First layer: Oracle database system layer, determining whether a session can be established.
- 2) Second layer: Application usage privileges, checking and verifying which applications a user can use.
- 3) Third layer: Object-level privileges in the Oracle database, determining whether a user can manipulate the corresponding objects. Object-level privileges are set through custom Oracle roles.

### Security Design Example

```sql
create profile grace_5 limit
failed_login_attempts 3
password_lock_time unlimited
password_life_time 30
password_grace_time 5
sessions_per_user 2
cpu_per_session 10000
idle_time 60
connect_time 480;
create user comm identified by comm
default tablespace data
temporary tablespace tsp_temp
quota 15M on data profile grace_5;
grant connect,resource to comm;
```

## 4.4.4 ORACLE Object Design

Database application systems inevitably require a large number of schema objects. These objects should be reasonably planned to minimize problems such as performance degradation, insufficient tablespace, and inadequate user privileges caused by poor design.

### Tables

When creating tables, the following considerations should be noted:

- 1) Use names that adhere to naming conventions and are descriptive for table names, column names, constraint names, index names, and cluster names.
- 2) Establish complete and detailed documentation.
- 3) All tables should be normalized (at least to Third Normal Form).
- 4) Define columns that allow NULL values and reserve appropriate storage space.
- 5) Use clustered tables appropriately and reserve storage space.
- 6) Table segments should be placed in separate tablespaces.
- 7) To reduce storage fragmentation, extent sizes should ideally be an integer multiple of the data block size.
- 8) For tables with few rows that are frequently used in the application system, consider using the CACHE option, which allows them to remain in memory for extended periods, avoiding repeated reads and improving performance.

### Triggers

Triggers are provided to users as a supplement to Oracle's standard features. They are commonly used to implement the following functions:

- 1) Automatically generate derivable column values.
- 2) Prevent invalid processing.
- 3) Enhance complex security verification.
- 4) Enhance referential integrity across nodes in a distributed environment.
- 5) Enforce complex business rules.
- 6) Provide transparent event logging.
- 7) Provide advanced auditing.
- 8) Maintain synchronization of table replicas.
- 9) Collect statistics on table access.

Although triggers can implement many functions, avoid using triggers for functionality that can be implemented by other means. Too many triggers lead to complex internal dependencies, making maintenance and management complicated. Pay special attention to keeping trigger statements short, and do not create recursively invoked triggers (for example, an AFTER UPDATE trigger on an object that also performs an UPDATE operation on that same object).

### Indexes

Once an index is created, its use and maintenance are automatically handled by Oracle. When using it, note:

- 1) Indexes can speed up queries but slow down modification operations; for tables that are frequently modified, minimize index creation.
- 2) Index segments should be stored in separate tablespaces.
- 3) To reduce storage fragmentation, extent sizes should be an integer multiple of the data block size.
- 4) To avoid generating excessive redo logs during index creation and modification, which affects system performance, use the NOLOGGING option when creating large indexes.
- 5) Since index entries are shorter than data rows, a single data block can hold more index entries than data rows. To improve concurrency for index operations at the data block level, you can appropriately increase the value of the INITRANS parameter.
- 6) PCTFREE in an index is used only at index creation. For monotonically increasing index column values, PCTFREE can be set low. Because new index entries are always appended to existing entries and do not need to be inserted between two existing entries, there is no need to reserve excessive space. If index column values are arbitrary, more space may need to be reserved.

### Views

Operations on views are similar to those on tables; wherever a table can be used, a view can generally be used as well. Views can be used for security control and simplifying queries. Views can only be created or dropped, not modified.

### Sequences

Application systems often use sequence numbers. The question is how to ensure that sequence numbers are consecutive and non-repeating among concurrent users. A sequence generator is a schema object in the database that can solve this problem and provide automatic management and maintenance of sequence numbers for application system developers. The parameter SEQUENCE_CACHE_ENTRIES in Init.ora is related to the sequence generator and affects the number of sequence numbers that can be retained in memory.

### Stored Procedures

Stored procedures can be called from the body of another stored procedure or from a trigger. A stored function can be called from a SQL statement, and its usage is the same as calling Oracle built-in SQL functions. When creating a stored procedure, attention should be paid to the schema ownership of the stored procedure.

### Synonyms

Synonyms can be used to hide the schema of schema objects in an application system.
