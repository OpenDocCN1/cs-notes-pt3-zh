

## 2.2.1.5 Resource Management

- PROFILE specifies dynamic resource limits for users. If no resource limit file is specified when creating a user, a configuration file called DEFAULT (the default configuration) is used. A resource limit file can limit the resources required by an individual call or by an entire session.

```sql
CREATE PROFILE filename LIMIT
  SESSIONS_PER_USER n|UNLIMITED  --Number of concurrent sessions allowed for each user
  CPU_PER_SESSION n|UNLIMITED  --Amount of CPU time used by each session, in 1% seconds
  CONNECT_TIME n|UNLIMITED  --Time connected to the database (minutes)
  LOGICAL_READS_PER_SESSION n|UNLIMITED  --Number of blocks read during a session
  ........ ;
```

- The purpose of limiting users' dynamic resources is security. The dynamic resources allocated to a user should be commensurate with the user's normal business activities. If a user's resource consumption exceeds the allocated limit, it indicates that the user is performing “unauthorized” work. The system usually prevents such behavior by terminating the session, rolling back the current transaction, and returning an error message.

## 2.2.1.6 Auditing

- The DBA needs to know what operations users have performed on tables, how many times users have logged in, and other database usage information in order to manage the system. Auditing is an important method used by the DBMS to monitor user activities and ensure system security. ORACLE writes audit records to the Audit trail table, which can be viewed to examine database activity.

- Audit users: `AUDIT statement option [BY user] [BY ACCESS|SESSION] [WHENEVER [NOT] SUCCESSFUL];`
  - BY user audits the specified user; by default, all users are audited;
  - BY ACCESS audits every SQL statement, while BY SESSION audits the same SQL statement only once during a session (to save resources); by default, all statements are audited;
  - WHENEVER [NOT] SUCCESSFUL audits successful or unsuccessful operations; by default, both successful and unsuccessful operations are audited.

- Example: `AUDIT select table, update table BY user1`
  
  Audits query or table/view modification operations performed by user1.

- Audit objects: `AUDIT option | ALL ON [schema.]object [BY ACCESS | SESSION] [WHENEVER [NOT] SUCCESSFUL];`

- Example: `AUDIT insert, update ON user1.student`
  
  Audits insert and update operations on the student table of user1.

- Viewing audit information:
  - `USER_AUDIT_TRAIL` - Defined audit information
  - `DBA_AUDIT_TRAIL` - Audit results
  - `AUDIT_ACTIONS` - Auditable commands

- Revoke auditing: `NOAUDIT...`

## 2.2.2 Integrity Constraints

- Database application designers and DBAs can establish rules for each data item in advance, requiring that data entered into the database comply with these rules. These rules are called integrity constraints.

- There are three ways to implement data integrity: application interface programming, defining constraints when defining tables, and describing integrity through trigger programming. The latter two methods are provided by the DBMS and are independent of the client, which can reduce the network burden.

- 2.2.2.1 Integrity Constraints in Create table
- 2.2.2.2 Modifying Integrity Constraints with Alter table
- 2.2.2.3 Triggers

### 2.2.2.1 Integrity Constraints in Create table

- `CREATE TABLE [schema.]tablename (colname datatype [DEFAULT value|NULL] [column-level constraint|table-level constraint][,colname...]);`

- Column-level constraints: `NOT NULL or [CONSTRAINT constraint_name] UNIQUE|PRIMARY KEY|CHECK(condition)|REFERENCES table[(col,...)] [ON DELETE CASCADE]`

- Table-level constraints: `[CONSTRAINT constraint_name] UNIQUE(col,col...)|PRIMARY KEY (col,col...)|CHECK(condition)|FOREIGN KEY (col,col...) REFERENCES table[(col,...)] [ON DELETE CASCADE]`

- To modify constraints, this clause can be used to assign a name to a column or table constraint.

- If this specification is omitted, the primary key of the referenced table is used.

- `NOT NULL`, `UNIQUE`, and `PRIMARY KEY` can implement entity integrity; `FOREIGN KEY REFERENCES` can define referential integrity; `ON DELETE CASCADE` indicates cascading deletion.

- Example:

```sql
create table orders (ordno integer not null, month char(2),
  cid char(4) not null,aid char(4) not null, pid char(4) not null,
  qty integer not null constraint qck check(qty>=0),
  dollars float default 0.0 constraint dck check(dollars>=0.0),
  primary key (ordno),
  constraint cidref foreign key (cid) references customers,
  constraint aidref foreign key (aid) references agents,
  constraint pidref foreign key (pid) references products);
```

### 2.2.2.2 Modifying Integrity Constraints with Alter table

- The ALTER TABLE statement allows the DBA to change the structure of a table, add or modify columns, and add or delete various constraints. (Pay attention to privileges.)

```sql
ALTER TABLE tablename
  [ADD (col type [DEFAULT value|NULL] [column-level constraint|table-level constraint][, colname...])]
  [DROP COLUMN col|(col, col...)]
  [MODIFY (col type [DEFAULT value|NULL])]
  [DROP CONSTRAINT constraint_name]
  [DROP PRIMARY KEY];
```

- If a table constraint has been named, that name can be used to DROP the constraint, and a new table constraint can be added with the ADD clause. Note that adding a new column affects the physical storage of rows and may prevent them from being stored in their current locations on disk.

### 2.2.2.3 Triggers

- A trigger is similar to a procedure or function and **is a program block**, but a procedure is called explicitly, whereas a trigger is called automatically when an event occurs. A trigger does not accept parameters.

- A trigger can cause an action to be executed and can be used to implement **procedural constraints**. Constraints created when a table is defined are called **nonprocedural constraints**.

- The Sybase database was the first to support triggers. Oracle, DB2 UDB, Informix, and SQL Server now support them, but Core SQL-99 does not.

- When defining trigger actions, each product uses its own procedural language. The following example uses Oracle for illustration.

```sql
CREATE [OR REPLACE] TRIGGER trigname
  BEFORE|AFTER|INSTEAD OF                --Trigger timing
  INSERT|DELETE|UPDATE [OF col,...]--Triggering event
  ON tabname                             --Tables only
  FOR EACH ROW|STATEMENT                 --Row-level trigger
  [WHEN (condition)] BEGIN ..PL/SQL block.. END;
```

Trigger timing specifies whether the trigger fires before or after the event, or only fires without executing the event;

The triggering event can be an insert, delete, update, or a combination of the three;

A row-level trigger executes the trigger body separately for each row satisfying the WHEN condition, while a statement-level trigger fires only once when the event occurs;

In a row-level trigger, new and old values can be distinguished. The value before the event is `old`, and the value after the event is `new`. A colon (`:`) must precede `old` and `new`;

The logical variables `inserting`, `deleting`, and `updating` can be used in a trigger. If an INSERT operation occurs, the `inserting` variable is true; otherwise, it is false.

- Example:

```sql
create or replace trigger t_c
  after update on customers
  for each row when (new.discnt>15.0)
  declare v1 number;
    v2 number;
  begin
    v1 := :old.discnt;
    v2 := :new.discnt;
    dbms_output.put_line('old:'||to_char(v1)
      ||'new:'||to_char(v2));
  end;
```

Explanation: After a modification operation occurs on the `customers` table, the old and new discount rates whose values are greater than 15 are displayed.
