### 6.1.1 UML的主要内容

### 什么是UML？

- UML表示Unified Modeling Language
- UML把下面一些先进的技术结合起来：
  - 数据建模概念（实体关系图）
  - 商业建模（工作流）
  - 对象建模
  - 组件建模
  - 行为建模
- UML是用来对软件相关系统进行可视化、规范、创建和建立文档的标准语言
- UML可以用在所有的过程中，贯穿整个开发周期，并跨越不同的实现技术

### 为什么需要UML？

- 1. 面对众多的建模语言，用户由于没有能力区别不同语言之间的差别，因此很难找到一种比较适合其应用特点的语言；
- 2. 众多的建模语言实际上各有千秋；
- 3. 虽然不同的建模语言大多类同，但仍存在某些细微的差别，极大地妨碍了用户之间的交流。

> 因此在客观上，极有必要在精心比较不同建模语言优缺点及总结面向对象技术应用实践的基础上，组织联合设计小组，根据应用需求，取其精华，去其糟粕，求同存异，统一建模语言。

### 6.1 UML概述

- **UML（Unified Modelling Language）表示法**
  - UML的符号、文本语法、图形机制
  - 用来表达应用问题在需求、设计和实现级的模型
- **UML语义**
  - 用UML表示法描述UML的元模型
  - 元模型为UML的所有语法元素的语义提供定义性说明
- **UML的可视化建模机制**分为静态和动态：
  - 静态机制包括：用例图、类图、对象图、包图、构件图、配置图
  - 动态机制包括：顺序图、合作图、状态图、活动图

### 6.1.2 UML的历史

- 80年代末期到90年代，各种OO软件开发方法纷纷涌现：OOA/OOD, Booch, OMT, OOSE... ...
- 1994年10月，Booch和Rumbaugh统一Booch93和OMT2，发布UML 0.8
- 1995年秋，Jacobson加盟Rational，1996年6月发布UML 0.9，1996年10月发布UML 0.91
- 1997年UML获众多著名软件公司的支持，11月被OMG接纳为标准
- 1998年UML发展到UML 1.4，相应的软件开发环境Rational Rose正式推出
- 2003年UML发展到UML 2.0

### 6.1.3 UML的特点

- 集成众多OO软件开发方法的表示机制的优点，统一化、标准化、系统化
- 用宽谱语言机制支持软件开发全过程
- 具有较完善、配套的软件开发环境（如Rational Rose）
- 已成为OO建模语言的事实上的工业标准，发展前景广阔

### 6.2 UML静态建模机制

### 6.2.1 用例图

### 1. 用例

用户与计算机之间一次典型的交互作用，引发系统执行一系列动作，动作执行的结果能被用户（或外部实体）觉察到

- 用例描述某种用户（或外部实体）可见的动作，实现一个具体的完整的用户目标
- 用例不同于用户与软件系统的交互动作序列

### 2. 用例图

描述执行者(Actor)与用例，以及用例与用例之间的关系

### USE-CASE DIAGRAM

Shows the system’s use cases and which actors interact with them

Actor, use case, and association

![](img/134871fe98cb20245c2dff1445580eb9_123_0.png)

### 3. 用例图中的关系

- Actor与用例之间的关系：触发执行，交换信息
- 扩展关系：用例A与B相似，但B的动作较A多，含有A所不具备的一些特殊情况下的处理动作，则将B作为A的扩展
- 使用关系：如果多个用例A₁，…，Aₙ中存在公共的动作B，可将B抽出，Aᵢ使用B（i=1，2，…，n）

![](img/134871fe98cb20245c2dff1445580eb9_126_0.png)

图 6.10 “家庭保安系统”的用例图

### 4. 用例模型的获取

### 4.1 获取Actor

- 谁使用系统的各项功能
- 谁需要系统支持其工作
- 谁来维护、管理、配置系统
- 谁对系统产生的结果感兴趣
- 系统需要与哪些外部实体交互
- 观察用户的工作流程
- 标识外部事件并观察用户的反映

### 4.3 标识Actor及用例之间的关系

- 利用“扩展”表示变异处理行为
- 利用“使用”抽取公共行为，简化用例图

### 4.4 约束

- 每个用例必须至少与一个Actor相连接

### 6.2.2 类图

### 1. 类图

类图是UML中OO模型的基础，它们描述系统的静态结构

包图描述系统的分治结构

类图主要描述：

- 对象的类型、属性与操作
- 类之间的静态关系：关联、子类型、聚合和构成、依赖等
- 作用于上述关系之上的约束

![](img/134871fe98cb20245c2dff1445580eb9_134_0.png)

### 2. 类图的抽象层次

- **概念层**：描述问题域中的概念及它们之间的静态关系
- **规范层**：描述类型（去除方法体之后的类）及其关系（软件结构）
- **实现层**：描述类及其关系

### 3. 属性

- 定义形式：可见性  属性名： 类型=缺省值 [约束特性]
- 概念层：同OOA/OOD，描述问题域中的概念的属性
- 规范层：隐含get/set方法
- 实现层：隐含类中成员变量的说明

### 4. 操作

- 定义形式：可见性 操作名(参数表)：返回类型 {约束特性}
- 概念层：问题域中的任务描述
- 规范层：操作的接口描述
- 实现层：方法体

### 5. 关联

![](img/134871fe98cb20245c2dff1445580eb9_138_0.png)

表示两个类之间语义上联系

- ♣ 概念层：两个概念之间的联系
  - 关联具有两个角色（Roles），可以对角色命名，匿名角色使用目标类作为名字
- ♣ 规范层：隐含类型之间的查询职责和关系维护职责

```
class Order { public Customer getCustomer();
                  public Enum enumOrderItems(); }
```

- ♣ 实现层：隐含两个类在各自的成员变量中相互包含或引用

```
class Order { private Customer       m_customer;
                  private ItemVector     m_orderItems; }
class Customer { private OrderVector m_orders; }
```
