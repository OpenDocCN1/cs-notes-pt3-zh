
## 基于状态的行为建模的范围

- Java AWT、MS/Windows、Unix X-Windows 等的 GUI 界面元素的行为；
- 商业对象（类）的行为和它们的生存循环：订单，顾客，存货单等；
- 通信设备：路由器、modem 控制器、电话、手持无线设备等；
- 具有重试、重新开始、重新恢复功能的设备驱动器；
- 命令语法分析器；
- 长期的数据库事务；
- 移动控制系统：航空电子控制系统、自动巡航系统、机器人等。

## 基于状态的测试设计

- 实现必须符合指定的状态机的约束。
- 了解实现如何与观察到的约束不相符合，为测试设计提供了重点，也为评估测试设计策略提供了基准。

## 控制错误

- 一个控制错误允许一个不正确的事件序列被接受或产生一个不正确的输出动作序列。
  - 例如：交通灯直接由红变绿

## 控制错误的类型

- 丢失的或不正确的转换
- 丢失的或不正确的事件
- 丢失的或不正确的动作
- 多余的、丢失的或错误状态
- 潜行路径（一个不应被接受的消息被接受）
- 非法消息的失效（一个不期望的消息引起的失效）
- 陷阱门（实现了没有定义的消息）

## 开发可测模型

- 并非所有的实现都非常适合基于状态的测试。
- 当被测实现的责任包括顺序行为时，则有效的测试设计依赖一个完全的、一致的、正确的状态模型的开发。
- 一个测试模型必须正确地表示需求，准确地反映被测实现。
- 使用检查表。

## 状态模型检查表（二）：状态名称

### 2. 不好的状态名经常是不完全和不正确设计的征兆

- 2.1 状态名称在应用领域中是有意义的；
- 2.2 当怀疑一个状态名时，就把它删掉；
- 2.3 不要用“等待的x”或“等待x”作为状态名；
- 2.4 状态名没有表达不相关的信息；
  - 2.4.1 没有名称重复状态变量不变式——100<x<1000；
  - 2.4.2 没有名称描述和动作相关的过程——compute x；
  - 2.4.3 没有名称用于输入描述——鼠标点击，用户参数。

## 状态模型检查表（三）：受监视转换

### 3. 条件转换

- 3.1 在状态转换的条件集中，条件表达式产生的真值的全部范围必须被覆盖；
- 3.2 对一个转换，每一个条件都和其它的条件相互排斥；
- 3.3 一个抽象状态模型的条件变量是被测类的客户端提供的输入；
- 3.4 一个具体类状态模型的条件变量是由被测类的实现定义——例如self或this；
- 3.5 条件表达式的计算对被测类不会产生任何副作用。

## 状态模型检查表（四）：好的子类行为

### 4. 子类的行为是良定的

- 4.1 子类没有删除任何超类状态：在超类中接受的转换也被子类接受；
- 4.2 子类不会减弱任何超类状态的状态不变量；
- 4.3 子类不会破坏任何超类状态的状态不变量；
- 4.4 子类或者加强超类状态不变量，或者仅仅继承它；
- 4.5 子类可以添加由子类引入的实例变量定义的正交状态；
- 4.6 超类转换中所有的条件和子类转换相同或弱于子类；
- 4.7 所有被继承的输出动作和子类的责任一致；
- 4.8 发送到对象的消息不会对被测类产生副作用。

## 状态模型检查表（五）：健壮性

### 5. 模型规定了健壮行为

- 5.1 对没有被明确拒绝的事件，有一个明确规定的错误处理和异常处理机制；
- 5.2 对于一个非法消息的结果，实现的状态不会被错误地改变、被破坏或没有被定义；
- 5.3 对每一个动作，没有改变和这个动作相关的结果状态的副作用或异常；
- 5.4 对前置、后置条件，不变式的冲突，规定了明确的异常、错误注册和恢复机制；
- 5.5 对丢失或延迟的事件规定了明确的异常、错误注册和恢复机制；
- 5.6 对每一个超时，规定了明确的异常、错误注册、恢复机制；
- 5.7 被测系统的目标环境的主要和不重要的失败模式被分类，对每个失败模式，规定了一个明确的异常机制；
- 5.8 对每一失败模式，指定了结果状态，或硬性的终止状态；
- 5.9 重新开始机制被建模并定义了一个到一个正常状态的路径。
