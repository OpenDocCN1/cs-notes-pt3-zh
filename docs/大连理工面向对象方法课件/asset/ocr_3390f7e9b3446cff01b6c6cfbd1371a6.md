# 5. 变化

+   1）一些方法可能会改变被观察机制的内部问题。

+   2）观察者不可能知道实现的全部细节。因此，观察者必须能够在不知道实现细节的情况下工作。

+   3）通知机制通常由观察者对象负责维护。观察者可以注册和注销，并在被观察对象发生变化时得到通知。

+   4）如果通知是同步的，那么被观察对象必须等待所有观察者完成处理；如果通知是异步的，则需要额外的线程或事件机制。

+   5）观察者模式的一个缺点是可能导致通知链过长，从而增加系统的复杂性。

```
void MySubject::Operation (int newValue) {
    BaseClassSubject::Operation(newValue);
    // trigger notification

    _myInstVar += newValue;
        // update subclass state (too late!)
}
```

在另一个例子中，基类中的操作可能先触发通知，然后子类才更新自己的状态，这可能导致观察者得到不一致的信息。

```
void TextField::OnChange (TextRange r)
{
    ReplaceRange(r);        // redefined in subclasses
    Notify();
}
```

观察到这一点，在实际中可以采用更合理的设计来避免上述问题。

+   6）避免将变化聚集在单一的更新一处/触发器。观察者模式的实现通常需要注册和注销观察者。

它是一个很好的设计原则。目前观察者通常被分为两类：一类为观察者，另一类为被观察者。我们将之称为模型（model）和视图（view）。

+   7）模型是应用程序的核心部分，直接表示应用程序的数据和逻辑；视图负责显示模型中的数据。

+   8）模型和视图之间通过观察者模式进行通信。模型发生变化时，视图可以得到通知并更新显示。

+   a) 一个模型可以有多个视图，这些视图可以显示同一个模型的不同方面。

+   b) 视图不会修改模型中的数据，而是通过控制器与模型进行交互。

+   c) 模型和视图之间的通信是松耦合的，模型不需要知道视图的具体实现。

+   9）当多个视图需要共享同一个模型时，可以使用观察者模式。模型中的变化会自动通知所有相关视图。
