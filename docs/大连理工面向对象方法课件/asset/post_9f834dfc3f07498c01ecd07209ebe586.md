
## 三. 我们应该注意什么？

简单工厂模式（包括其他工厂）是用来创建实例对象的。所以以后在new（创建对象）时就要多个心眼，是否可以考虑使用工厂模式，虽然这样可能多做一些工作，但会给系统带来更大的可扩展性和尽量少的修改量。

## 工厂方法模式

### Factory Method Pattern

## 1. 引言

### 简单工厂模式

**优点**：一个工厂处于对产品类实例化的中心位置上，它知道每个产品，它决定哪一个产品类应当被实例化。允许客户端相对独立于产品创建的过程，在一定程度上支持了“开闭原则”。

**缺点**：对“开闭原则”的支持不够。因为如果有新的产品加入到系统中，就需要**修改工厂类**，将必要的逻辑加入到工厂类中。

工厂方法模式保持了简单工厂的优点，克服了它的缺点。

**首先**，在该方法中，核心的工厂类不再负责所有产品的创建，而是将具体创建的工作交给子类去做。这个核心类则变成了**抽象工厂角色**，仅负责给出具体工厂子类必须实现的接口，而不接触哪个产品类应当被实例化这种细节。

**其次**，这种抽象的结果，使这种工厂方法模式可以用来**允许系统在不修改具体工厂角色的情况下引进新产品**，这显然比简单工厂要优越。

## 2. 工厂方法模式的结构

(1)如图所示。

![](img/3b4669cf00b2833fe526284506f3f342_38_1.png)

- 1. 抽象工厂（Creator）角色：担任这个角色的是工厂方法模式的核心，它是与应用无关的。任何在模式中创建对象的工厂类必须实现这个接口。在上面的系统中这个角色由接口Creator 扮演；在实际的系统中，这个角色也常常使用抽象类实现。

- 2. 具体工厂（Concrete Creator）角色：担任这个角色的是实现了抽象工厂接口的具体工厂角色包含有与应用密切相关的逻辑，并且受到应用程序的调用以创建产品对象。在本系统中给出了两个这样的角色，也就是具体类ConcreteCreator1 和ConcreteCreator2。

- 3. 抽象产品（Product）角色：工厂方法模式所创建的对象的超类型，也就是产品对象的共同父类或共同拥有的接口。在本系统中，这个角色由接口Product 扮演；在实际的系统中，这个角色也常常使用抽象类实现。

- 4. 具体产品（Concrete Product）角色：这个角色实现了抽象产品角色所声明的接口。工厂方法模式所创建的每一个对象都是某个具体产品角色的实例。在本系统中，这个角色由具体类ConcreteProduct1 和ConcreteProduct2 扮演，它们都实现了Product接口。

- 5. 客户端角色（Client）：为了说明这个系统的使用办法，特地引进了一个客户端角色Client。这个角色创建工厂对象，然后调用工厂对象的工厂方法创建相应的产品对象。

### (2) 示意性代码框架：

```java
public interface Creator//抽象工厂类
{
    public Product factory();
}

public interface Product//抽象产品类
{
}

public class ConcreteCreator1 implements Creator//具体工厂类1
{
    public Product factory()
    {
        return new ConcreteProduct1();//返回产品 1 的对象
    }
}

public class ConcreteCreator2 implements Creator//具体工厂类 2
{
    public Product factory()
    {
        return new ConcreteProduct2(); //返回产品 2 的对象
    }
}

public class ConcreteProduct1 implements Product//具体产品类 1
{
    public ConcreteProduct1()
    {
        //do something
    }
}

public class ConcreteProduct2 implements Product//具体产品类 2
{
    public ConcreteProduct2()
    {
        //do something
    }
}

public class Client//客户端
{
    Creator creator1,creator2;
    Product prod1,prod2;
    public static void main (String[] args)
    {
        creator1=new ConcreteCreator1();
        creator1.factory();
        creator2=new ConcreteCreator2();
        creator2.factory();
    }
}
```

### （3）工厂方法模式和简单工厂模式

区别：工厂方法模式和简单工厂模式在结构上的区别不是很明显的。工厂方法模式的核心：是一个抽象工厂类，具体工厂类派生于抽象工厂类；而简单工厂模式把核心：放在一个具体类上。

联系：工厂方法模式可以允许很多具体工厂类从抽象工厂类中将创建行为继承下来，从而可以成为多个简单工厂模式的综合，进而推广了简单工厂模式。

工厂方法模式退化后可以变得很像简单工厂模式。设想如果非常确定一个系统只需要一个具体工厂类，那么就不妨把抽象工厂类合并到具体的工厂类中去。由于只有一个具体工厂类，就得到了简单工厂模式。

工厂方法模式的优点：工厂方法模式之所以有一个别名叫多态性工厂模式，显然是因为具体工厂类都有共同的接口，或者都有共同的抽象父类。如果系统需要加入一个新的产品，那么所需要的就是向系统中加入一个这个产品类以及它所对应的工厂类。没有必要修改抽象工厂角色或者其他已有的具体工厂角色。对于增加新的产品类而言，这个系统完全支持“开-闭”原则（一个软件实体应当对扩展开放，对修改关闭）。

## 3. 工厂方法模式在农场系统中的实现 (p103)

### (1) 系统的优化

现在继续考虑农场的管理系统。在“简单工厂（Simple Factory）模式”里，讨论了支持水果类作物的系统。在那个系统中，有一个全知全能的园丁角色（FruitGardener），控制所有作物的种植、生长和收获。现在这个农场的规模变大了，而同时发生的是管理更加专业化了。

过去的全能人物（园丁）没有了，每一种农作物都有专门的园丁管理，形成规模化和专业化生产。

### (2) 系统的设计

取代了过去的全能角色是一个抽象的园丁角色，这个角色规定出具体园丁角色需要实现的具体职能，而真正负责作物管理的则是负责各类作物的具体园丁角色。
这里仍然考虑前面所讨论过的植物，包括葡萄（Grape）、草莓（Strawberry）以及苹果（Apple）等。专业化的管理要求有专门的园丁负责专门的水果，比如苹果有“苹果园丁”负责，草莓有“草莓园丁”负责，而葡萄有“葡萄园丁”负责。
这些“苹果园丁”、“草莓园丁”、“葡萄园丁”都是实现了抽象“水果园丁”接口的具体工厂类，而“水果园丁”则扮演了抽象工厂角色。
