

## Example

R = (A, B, C)
F = { A → B, B → C }
Key = {A}

Any relation schema with two attributes is in BCNF.

R is **not in BCNF** (∵ F⁺ = {A → B, B → C, A → C, …}, for B → C, **B is not a key**)

Decomposition R₁ = (A, B), R₂ = (B, C)

- **R₁ and R₂ in BCNF.** (A is the key for R₁, B is the key for R₂)
- **Lossless-join decomposition.** (R₁ ∩ R₂ = B, and B is the key for R₂)
- **Dependency preserving.** (F₁ = {A → B} holds on R₁, F₂ = {B → C} holds on R₂)

## Testing for BCNF

- To check if a non-trivial dependency \(\alpha \rightarrow \beta\) causes a violation of BCNF:
  1. compute \(\alpha^+\) (the attribute closure of \(\alpha\)), and  
  2. verify that if \(\alpha^+\) includes all attributes of \(R\), that is, \(\alpha\) is a superkey of \(R\).

- Simplified test: To check if a relation schema \(R\) is in BCNF, it suffices to check only the dependencies in the given set \(F\) for violation of BCNF, rather than checking all dependencies in \(F^+\)
  - If none of the dependencies in \(F\) causes a violation of BCNF, then none of the dependencies in \(F^+\) will cause a violation of BCNF either.

\(\cdot \cdot \cdot F^+\) 是由 Armstrong 的 3 个公理从 \(F\) 推出的，而任何公理都不会使 \(FD\) 左边变小(拆分)，故如果 \(F\) 中没有违反 BCNF 的 FD(即左边是 superkey)，则 \(F^+\) 中也不会。

## Testing for BCNF(cont.)

However, using only F to test for BCNF may be incorrect when testing a relation in a decomposition of R.

- E.g. Consider \( R(A, B, C, D) \), with \( F={A \rightarrow B, B \rightarrow C} \)
- R is in BCNF ? Which is candidate key?
- Decompose \( R \) into \( R_1(A,B) \) and \( R_2(A,C,D) \)
- Neither of the functional dependencies in \( F \) contain only attributes from \( (A,C,D) \), so no FD violates BCNF, we might be mislead into thinking \( R_2 \) satisfies BCNF.
- In fact, dependency \( A \rightarrow C \) in \( F^+ \) shows \( R_2 \) is not in BCNF.

(可在F下判别R是否违反BCNF，但须在F+下判别R的分解式是否违反BCNF.)

## (2) BCNF Decomposition Algorithm

result := {R};
done := false;
compute F⁺;
while (not done) do
if (there is a schema Rᵢ in result that is not in BCNF)
then begin
let α → β be a nontrivial functional dependency that holds on Rᵢ such that α → Rᵢ is not in F⁺, and α ∩ β ≠ ∅;
result := (result − Rᵢ) ∪ (α, β) ∪ (Rᵢ − β);
end
else done := true;

Note: at last, every sub-schema is in BCNF, and the decomposition is lossless-join.

> It means there is nontrivial FD α → β in Rᵢ , and α is not a key.
> 将Rᵢ分解为二个子模式：Rᵢ₁=(α, β )和Rᵢ₂=(Rᵢ − β)，α是 Rᵢ₁ Rᵢ₂ 的共同属性

## Example of BCNF Decomposition

R = (branch-name, branch-city, assets, customer-name, loan-number, amount)
F = { branch-name → branch-city assets, loan-number → amount branch-name }

Key = { loan-number, customer-name },
∴ (loan-number, customer-name ) +=R

### Decomposition

R1 = (branch-name, branch-city, assets),
R2 = (branch-name, customer-name, loan-number, amount),
R3 = (loan-number, branch-name, amount)
R4 = (customer-name, loan-number)

### Final decomposition :

R1, R3, R4 , all in BCNF.

## BCNF and Dependency Preservation

It is not always possible to get a BCNF decomposition that is dependency preserving.

### Example:

$R=(J,K,L)$ — J学生、K课程、L教师

$F=\{JK\to L,\ L\to K\}$

- Two candidate keys = $JK$ and $JL$
- $R$ is not in BCNF. (∵ for $L\to K$, $L$ is not a key)
- Any decomposition of $R$ will fail to preserve $JK\to L$
  - E.g. $R1=(L,K), R2=(J,L)$, ⊆ BCNF, but not dependency preserving

J---student, K---course,
L---teacher（一门课有多个教师，一个教师上一门课，一个学生选多门课，一门课有多个学生选）

Therefore, we cannot always satisfy all three design goals:

- Lossless join
- BCNF
- Dependency preservation
